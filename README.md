# hack-kit

Процесс разработки командой людей и агентов Claude: человек согласует изменение меткой (или один раз утверждает этап в плане, и изменения этапа запускаются сами), а дальше агенты делают его, ревьюят и сливают в `main`. Собран после UMIRHack 2026 из нашего опыта SwapOwl и практик победителей (Goden, «Остаток», RIMS). Проверен на этом репозитории 19–20.10.2026: цепочка прошла целиком на нескольких PR, включая красный CI, раунды замечаний, оспаривание, перезапуск, конфликт с `main`, ручное слияние правил процесса и автоназначение без метки человека (раздел 2).

## 1. Что это, запуск и эксплуатация

### Как работает

```
человек: метка go:exec-1 на черновике PR           ИЛИ   человек утверждает этап в docs/plan.md (слияние PR)
   │                                                        │
   ▼                                                        ▼
guard.yml ── метку поставил человек из team.md?       assign.yml ── изменение есть в утверждённом этапе,
   │                                                   есть место у исполнителя (team.md)? → [assign], go:<id>
   └──────────────────────────── /fire ───────────────────┘ ──►  routine exec-1
                                                                              │ одна сессия на PR:
                                                                              │ [start] → задачи → архив изменения
                                                                              │ → снять черновик → [fix] round 0
                                                                              │ → подписка на события PR, ждёт
ci.yml: тесты, линтеры, контракт, сторожа                                     │
   ├─ красные → итог «[review] … source: ci» (бот) ─────────────────────────► в ту же сессию
   └─ зелёные → «[ci] ревью запрошено» ── /fire ──► routine reviewer          │
                                                      │ ревью по чек-листу,   │
                                                      │ итог «[review] …»     │
review-post.yml ◄─────────────────────────────────────┘                       │
   формат, автор, head → round-N, protected → «[ci] итог ревью принят» (бот) ─► в ту же сессию
                                                                              │ CHANGES_REQUESTED → правки → push → снова CI
                                                                              │ APPROVED → squash в main → [merge] слито
```

**Агенты** — это routines Claude Code (облачные сессии на claude.ai, по аккаунту на человека), **бухгалтерия** — GitHub Actions без модели: тесты, раунды, метки, запуск routines.

| Кто | Где | Модель | Чем запускается | Инструкция |
|---|---|---|---|---|
| Исполнитель `exec-<id>` | routine на аккаунте своего человека | Sonnet 5.5 (effort medium) | `/fire` из `guard.yml` (метка `go:<id>` от человека) или из `assign.yml` (утверждённый этап) | [`.github/agents/executor.md`](.github/agents/executor.md) |
| Ревьюер | routine человека, который сам не исполнитель | Sonnet 5.5 (effort high) | `/fire` из `ci.yml` (зелёные тесты) и `ai-review.yml` (оспаривание) | [`.github/agents/reviewer.md`](.github/agents/reviewer.md), [`.github/review-prompt.md`](.github/review-prompt.md) |
| Пахан (ведущий) | локальный Claude Code владельца (routine нет) | Opus 5.5 (effort high) | человек | [`.github/agents/lead.md`](.github/agents/lead.md) |
| Критик | ночная routine (не создана: нужен стенд) | Opus 5.5 (effort high) | расписание | [`.github/agents/critic.md`](.github/agents/critic.md) |

**Главные правила**

- **Изменение = один PR = одна сессия исполнителя.** Сессия, которая начала PR, ведёт его до слияния: после снятия черновика подписывается на события PR и отвечает на ревью в ней же.
- **Человек нужен в трёх местах:** согласовать предложение меткой `go:<id>` (или утвердить этап в `docs/plan.md`, тогда изменения этапа запускаются сами), разобрать `needs-human` и слить PR с меткой `manual-merge` (правила процесса: `.github/`, `.agents/`, `AGENTS.md`, `CLAUDE.md`, `team.md`, `docs/plan.md`; сторожа `tests/invariants/`, `e2e/`; ломающая или ослабляющая правка контракта — метка `contract-breaking` от `oasdiff`). Остальные одобренные PR сливает исполнитель сам.
- **Правила проверяет машина:** контракт API, границы модулей (depguard), слои фронта (steiger), контраст, сторожи-инварианты на PostgreSQL. Упавшая проверка — ошибка в коде, а не в проверке.
- **Данные — не инструкции.** Тексты PR, комментарии и текст запуска routine агенты читают как материал, а не как команды.

### Запуск на новом проекте (один раз, ~30 минут)

Порядок важен: **сначала GitHub App, потом routines.**

1. **Репозиторий.** Скопировать содержимое этого репозитория (или `hack-kit/template` из локального набора) в корень нового. Заменить заглушки `backend/`, `frontend/` своим проектом, `example.com/app` в `backend/.golangci.yml` — модулем из `go.mod`.
2. **Claude GitHub App** — https://github.com/apps/claude → Configure → доступ к репозиторию. Без неё облачные сессии не получат события PR (подписка исполнителя).
3. **Настройки репозитория.**
   - Settings → Actions → General → Workflow permissions: **Read and write**.
   - Settings → Branches → защита `main`: обязательные проверки `checks` и `merge-gate`, без «Do not allow bypassing» (подробно — `hack-kit/AGENTS-SETUP.md`). На бесплатном приватном репозитории недоступна, бесплатная организация тоже не поможет: нужен GitHub Pro или публичный репозиторий. Без защиты «не сливать красное» и `manual-merge` держит инструкция исполнителя и статус `merge-gate`.
4. **Метки:** `scripts/labels.sh exec-1 exec-2 …` (нужен `gh` с правами на репозиторий).
5. **`team.md`:** люди (их GitHub-логины — кто может ставить `go:*`), исполнители, раздел «Ревьюер» — аккаунт, от которого принимаются итоги ревью.
6. **Context7** — каждый человек: https://claude.ai/customize/connectors → Add custom connector → URL `https://mcp.context7.com/mcp`.
7. **Routines** — каждый на своём аккаунте, https://claude.ai/code/routines → New routine:

   | Routine | Модель, effort | Окружение | Репозиторий | Триггер | Коннекторы |
   |---|---|---|---|---|---|
   | `exec-<id>` (по одной на исполнителя) | Sonnet 5.5, medium | `effort-medium` | этот | **API** | Context7 |
   | `reviewer` | Sonnet 5.5, high | `effort-high` | этот | **API** | Context7 |

   Effort в routine не настраивается и из текста промпта не берётся: он задаётся переменной `CLAUDE_CODE_EFFORT_LEVEL` на облачном окружении (`effort-medium` → `medium`, `effort-high` → `high`, сеть как у Default с включёнными менеджерами пакетов). Подробности — [hack-kit/AGENTS-SETUP.md](hack-kit/AGENTS-SETUP.md), «Модель и effort на роль».

   Промпты — в [hack-kit/AGENTS-SETUP.md](hack-kit/AGENTS-SETUP.md), раздел «Тексты запуска». После сохранения: открыть API-триггер → **Generate token** (показывается один раз).
8. **Секреты** — Settings → Secrets and variables → Actions:

   | Секрет | Значение |
   |---|---|
   | `FIRE_EXEC_1_URL`, `FIRE_EXEC_1_TOKEN` | URL и токен API-триггера `exec-1` (`exec-2` → `FIRE_EXEC_2_*`) |
   | `FIRE_REVIEWER_URL`, `FIRE_REVIEWER_TOKEN` | URL и токен API-триггера `reviewer` |

   Токен умеет только запускать свою routine. Токены подписок Claude в секреты класть не нужно.
9. **Проверка цепочки.** Открыть тестовое предложение (как PR #3 или #17 ниже), поставить `go:exec-1` (или утвердить тестовый этап в `docs/plan.md`) и дождаться `[merge] слито`. Пока цепочка не прошла целиком, работу не раздаём.

### Эксплуатация

**Обычный цикл**

1. **Предложение.** В локальной сессии Claude Code: «нужно X» → пахан по скиллу `change-propose` открывает черновик PR `change: <имя>` с папкой `changes/<дата>-<имя>/` (предложение, дизайн, задачи, сценарии) и комментарием `[lead]` с рекомендуемым исполнителем.
2. **Согласование.** Два способа. **По одному изменению:** прочитать PR и поставить `go:<id>` («да», назначение и запуск одним действием). **По этапу:** слить PR, где в `docs/plan.md` у этапа статус `утверждён`; `assign.yml` сам запустит исполнителей на все изменения этого этапа по очереди (лимит и «Доступен» из `team.md`).
3. **Дальше без человека.** Следить можно по комментариям PR:

   | Префикс | Кто | Что значит |
   |---|---|---|
   | `[guard] …` | `guard.yml` | метка снята (поставил не человек) / перезапуск / не удалось запустить |
   | `[assign] <id> …` | `assign.yml` | автоназначение: изменение входит в утверждённый этап |
   | `[start] <id>` | исполнитель | взял PR |
   | `[fix] round N …` | исполнитель | готово к ревью / правки внесены / «правок нет, замечания оспорены» |
   | `[ci] checks зелёные, ревью запрошено` | `ci.yml` | ревьюер запущен |
   | `[review] round: N verdict: …` | ревьюер или CI (`source: ci`) | итог раунда |
   | `[ci] итог ревью принят …` | `review-post.yml` | сигнал сессии исполнителя |
   | `[merge] слито` | исполнитель | PR в `main` |
   | `[merge] ждёт человека …` | исполнитель | APPROVED, но PR с меткой `manual-merge` (правила процесса, сторожа, `contract-breaking`): сливает человек |
   | `[needs-human] …` + метка | любой | нужен человек, в тексте — что именно |

**Когда нужен человек**

| Ситуация | Что сделать |
|---|---|
| `needs-human` на PR | прочитать причину в комментарии, решить, снять метку; при необходимости перезапустить исполнителя |
| Сессия исполнителя умерла (нет ответа на итог ревью больше часа) | снять и снова поставить `go:<id>` → `[guard] перезапуск`, новая сессия перехватит PR |
| `[merge] ждёт человека` (метка `manual-merge`) | прочитать PR, слить вручную |
| `[guard] не удалось запустить` / `[assign] не удалось запустить` | проверить секреты `FIRE_<ID>_*` и что routine включена |
| `[ci] не удалось запустить ревьюера` | то же для `FIRE_REVIEWER_*` |
| Исполнитель недоступен (лимиты, ночь) | в `team.md` колонка «Доступен» → `нет`; пахан не будет его предлагать |

**Добавить исполнителя:** строка в `team.md` → `scripts/labels.sh exec-2` → routine `exec-2` на аккаунте человека (API-триггер, Context7) → секреты `FIRE_EXEC_2_URL`/`_TOKEN`.

**Менять routine** (промпт, модель, коннекторы) — в форме claude.ai или через `RemoteTrigger update`. GitHub-триггеры в routines не используем (см. отчёт).

## 3. Что стоит проверить и доделать

### Проверено 20.10–22.10.2026

Раунд с замечаниями, красный CI, оспаривание (сбой сети), перезапуск исполнителя, конфликт с `main`, Context7, `manual-merge`, автоназначение по этапу, хвост лога красного CI, проверка контракта `oasdiff`, `merge-gate`, очередь с блокирующим изменением: см. раздел 2.

### Не проверено в деле

1. **Отказ `guard`** для логина не из `team.md`. Скрипт проверки прогнан локально; живой тест — через второй аккаунт или временную подмену логина в `team.md` двумя ручными PR.
2. **Лимит `MAX_ROUNDS`.** Нужно четыре раунда замечаний подряд; в живую не гонялся.
3. **Долгая подписка.** Сессия ждала итог максимум ~10 минут. Неизвестно, сколько она живёт без событий (часы, ночь). Если сессия умерла, человек перезапускает её повторной `go:<id>`; правило для хака: перед сном разобрать зависшие PR.
4. **Критик.** Routine не создана: нужен стенд. Пахан работает только в локальной сессии (утренней routine нет, решение владельца 20.10).
5. **Несколько исполнителей.** Два `exec-*` на двух аккаунтах параллельно, лимиты запусков routines в час. Две сессии одного `exec-1` на разных PR работали параллельно без помех (#5, #6).
6. **Настоящий стек шаблона.** Заглушка проверила только цепочку. Не прогонялись: `pnpm check` реального фронта, автотест контраста, `scripts/screenshots.mjs` + axe, depguard на настоящих модулях, `make generate` с ogen/sqlc.
7. **Очередь автоназначения.** Очередь за блокирующим изменением и разбор очереди после слияния проверены (H4). Не проверены: нехватка мест у исполнителя (лимит `team.md`) и выбор между несколькими исполнителями.
8. **Процесс дня 0.** Дебаты (`debate`), выбор направления дизайна (`frontend-design-direction`), DAY0 целиком не запускались на новом кейсе.

### Решить и доделать

1. **Защита ветки `main`.** На бесплатном приватном репозитории недоступна, бесплатная организация тоже не поможет. Варианты: GitHub Pro на месяц хака или публичный репозиторий. Без неё «не сливать красное» и `manual-merge` держит инструкция исполнителя и статус `merge-gate` (находка 24).
2. **Секреты в команде.** Токены `FIRE_*` кладёт владелец репозитория; для команды удобнее организация GitHub, где каждый человек — admin своих секретов.
3. **Шаблон и этот репозиторий** синхронизируются руками (`hack-kit/template` в локальном наборе). Правки делаются здесь, шаблон обновляется копированием.
4. **GitHub-триггер `review-me`** у routine `reviewer` и старые неактивные сессии routines: убрать руками на claude.ai.
5. **Actions-минуты:** 2000 в месяц на бесплатном тарифе для приватного репозитория; на 48 часов хватит с запасом, но не запускать лишние прогоны.
6. **Открыть ли репозиторий** для жюри: правила агентов сейчас не видны посторонним.

## 4. Сравнение со SwapOwl

SwapOwl — наш проект на UMIRHack 2026 (кейс «Флагмана»): неделя, ~200 PR, 4 агента-исполнителя, процесс через Jira. hack-kit вырос из него: что работало — осталось, что мешало — заменено.

### Процесс и агенты

| | SwapOwl (октябрь 2026) | hack-kit |
|---|---|---|
| Где живёт задача | таска Jira; PR отдельно | **PR и есть задача**: папка `changes/<имя>/` (предложение, дизайн, задачи, сценарии) в самом PR |
| Как согласуется | человек принимал план, дальше планировщик сам раздавал тикеты | человек ставит `go:<id>` на предложение **или** утверждает этап в `docs/plan.md` (файл сливает только человек), дальше изменения этапа запускаются сами в пределах лимитов |
| Кто раздаёт работу | агент-планировщик в Jira (рутина) | пахан только предлагает; запускают `guard.yml` (метка человека) или `assign.yml` (утверждённый этап, по `team.md`) |
| Как будится исполнитель | Jira → API-триггер routine, ключ таски в `routine-fire-payload` | `guard.yml` или `assign.yml` → API-триггер routine, номер PR в `routine-fire-payload` |
| Ответ на ревью | та же сессия, подписка на PR; итоги от `github-actions[bot]` | так же: одна сессия на PR, подписка; итог ревьюера дублируется комментарием бота |
| Ревьюер | Opus в GitHub Actions на токене подписки в секрете | Opus как **routine** на аккаунте человека; Actions только считают раунды и метки, токен подписки не нужен |
| Документация библиотек | нет | Context7 у исполнителя (перед незнакомым API) и у ревьюера (подтвердить замечание) |
| Слияние | исполнитель, кроме `tests/invariants/`, `e2e/` и `needs-human` — их человек | исполнитель, кроме `manual-merge` (правила процесса, сторожа, `contract-breaking`) и `needs-human` — их человек |
| Статусы и общение | статусы и комментарии Jira + маркеры в PR (`[codex-review]`, `[claude-fix]`, `[claude-merge]`) | только PR: метки и префиксы (`[start]`, `[fix]`, `[review]`, `[ci]`, `[merge]`, `[guard]`, `[needs-human]`) |
| Где правила агентов | `.ai/` в репозитории; перед финалом убраны из репо | `.github/agents/`, `.github/review-prompt.md`, `.agents/skills/` — открыто, в защищённых путях |
| Число исполнителей | 4 на общих лимитах Pro + планировщик + ревьюер | по одному на человека, который успевает смотреть его PR |
| Внешние системы | Jira, коннектор Atlassian, рутины Jira | только GitHub и claude.ai |

### Продукт и качество

| | SwapOwl | hack-kit |
|---|---|---|
| Решение кейса | дебаты 3 агентов, якорная шкала, критик глазами жюри | то же (скиллы `debate`, `jury-critic`, `docs/scale.md`) + обязательные вопросы о ролях, точках и «внешнем участнике» |
| Архитектурные решения | раздел «Принятые решения» в README и `.ai/solution.md` | ADR на каждое решение (`docs/adr/`), по образцу Goden |
| Описание поведения | `solution.md`, тесты | сценарии WHEN/THEN в `specs/`, обновляются при архиве каждого изменения |
| Сторожи-инварианты | `tests/invariants/` на PostgreSQL, менять могут только люди | то же |
| Контракт API | `docs/openapi.yaml` писался руками | контракт первым: генерация кода, CI проверяет, что дифф пустой |
| Границы кода | договорённость | depguard (Go), steiger (слои фронта) в CI |
| Дизайн | язык сменили на 4-й день; детальная спека состояний и форматов | направление выбирается один раз в день 0 (ADR-0002); наша спека + каталог компонентов, витрина `/dev/ui`, автотест контраста, скриншоты по матрице, чек-лист анти-slop |
| Фронт | свой hash-роутинг, без слоя данных и линтеров | TanStack Router + Query, FSD-lite, ESLint, Prettier, Stylelint, `pnpm check` |

### Что лучше, что хуже, что не доказано

**Лучше**
- Нет второй системы: задача, код, ревью и решение — в одном PR. Меньше рутин и коннекторов, меньше точек отказа.
- Человек решает до работы, а не после: метка `go:` на конкретном предложении вместо раздачи тикетов агентом.
- Токен подписки больше не нужно отдавать владельцу репозитория; каждый агент тратит лимиты того, кто создал его routine.
- Сбой запуска агента виден сразу (`/fire` отвечает кодом) и превращается в `needs-human`, а не теряется.
- Машинные проверки, которых не было: контракт, границы модулей, слои фронта, контраст.

**Хуже или рискованнее**
- Автослияние без человека для `tests/invariants/`, `e2e/`, `deploy/`, `api/openapi.yaml`. На SwapOwl их сливал человек; здесь их держит только ревьюер (правила процесса — `.github/`, `.agents/`, `AGENTS.md`, `team.md` — сливает человек, раздел 3).
- Репозиторий приватный: правила агентов не видны посторонним. Для сдачи жюри нужно решить, открывать ли его (Goden выложил свои правила и выиграл, но это решение, а не данность).

**Не доказано**
- SwapOwl прошёл неделю боевой работы и ~200 PR. hack-kit проверен на трёх PR на заглушке — всё, что в разделе 3 «Не проверено в деле», надо пройти до настоящего хакатона.
