# Анализатор рисков оттока

**Хакатон РнД · Уровень Middle**

---

## Задача

Разработайте аналитическую систему, которая помогает маркетологам находить клиентов, которые в ближайшее время могут не продлить услуги или отказаться от них полностью.

Система должна отвечать на три вопроса:

1. Кому из пользователей платформы требуется внимание?
2. Почему возникает риск?
3. Сколько денег бизнес может потерять?

Результат необходим для выбора приоритетных клиентов и принятия маркетинговых решений.

### Примеры ситуаций для анализа

- Услуга скоро заканчивается, а автоматическое продление отключено.
- На аккаунте недостаточно средств для ближайших продлений.
- Услуга находится в статусе `prolong_wait`, особенно при отсутствии средств.

Вышеуказанные примеры ориентир для анализа. Команда самостоятельно выбирает признаки, формулу isk-score, коэффициенты, пороги уровней риска, периодичность прогноза и способ оценки денежных потерь. Выбор необходимо кратко объяснить жюри.

Исходные тестовые данные содержат текущие статусы, но не историю их изменений и даты удаления. Предполагается, что реальные данные поступают в систему в режиме реального времени произвольным способом. Исторические данные изменения статусов в предоставленном примере отсутствуют и лишь устанавливают DTO отношений между системой источником и текущим решением анализатора.

## Статусы услуг

| Статус | Описание |
|---|---|
| `active` | Услуга активна, всё хорошо, деньги капают |
| `suspended` | «Выключена»: услуга (например, сервер) выключена по требованию пользователя, деньги продолжают капать |
| `prolong_wait` | «Ожидает оплаты»: переход при истечении `expiresAt`. Статус сохраняется 5 дней в ожидании оплаты от клиента, после чего услуга переходит в `deleted` |
| `deleted` | «Удалена»: услуга удалена из-за неуплаты или по инициативе клиента |
| `blocked` | «Заблокирована»: продлить или пользоваться услугой дальше невозможно |

**Обоснование статусов:** указано в исходном задании.

## Поля

### Аккаунт

| Поле | Описание |
|---|---|
| `balance` | Основной баланс пользователя в реальных деньгах |
| `withdrawBalance` | Баланс, доступный для вывода в реальные деньги или на баланс платформы, заработанный на реферальной системе |
| `bonusBalance` | Баланс за промокоды и маркетинговые акции сервиса, который можно тратить на услуги |
| `bonusState` | Возможность тратить бонусный баланс |
| `totalReplenished` | Общая сумма реальных денег, которые пользователь пополнил на платформе за всё время |

### Услуга

| Поле | Описание |
|---|---|
| `pice` | Стоимость предоставляемой услуги (в исходных данных написано именно так) |
| `autoprolong` | Флаг «Автопродление»: позволяет списывать деньги с основного и бонусного баланса автоматически при наличии. Клиент может переключать его по своему усмотрению |
| `paymentTem` | Периодичность оплаты: `hour` (почасово), `week` (каждую неделю), `month` (каждый месяц), `quater_year` (каждые три месяца), `half_year` (каждые полгода), `year` (каждый год) |
| `name` | Произвольное название услуги |
| `sevices.status` | Текущий статус услуги (см. таблицу статусов выше) |

### Транзакция

| Поле | Описание |
|---|---|
| `transactions.status` | `pefomed` (выполнена) или `not_pefomed` (не выполнена, например, заказ создан, но не оплачен) |
| `type` | `prolong` (продление) или `order` (новый заказ) |
| `amount` | Сумма транзакции |

## Требования к веб-панели

1. **Веб-панель.** Показывает score каждого клиента, высокий, средний или низкий уровень риска и понятную причину оценки. Уровни можно дополнительно представить как обратную шкалу лояльности. При недостатке данных по клиенту необходимо явно указать отсутствие оценки.
2. **Топ клиентов под риском.** Таблица содержит ID, email, баланс, общую сумму пополнений и isk-score. Обязательна сортировка по ID, email, балансу и общей сумме пополнений в обе стороны (по убыванию и по возрастанию).
3. **Настройка модели.** Коэффициенты isk-score редактируются через панель. Изменения влияют на расчёт и сохраняются после перезапуска приложения.
4. **Денежная оценка.** Панель показывает, сколько бизнес может потерять, с учётом стоимости услуг, балансов аккаунтов и риска.

---

## Обязательные возможности

5. **Живое обновление.** После изменения данных или коэффициентов score, рейтинг и денежные показатели обновляются автоматически, без ручной перезагрузки страницы. Способ обновления выбирает автор решения.
6. **Endpoint `/metics`.** Отдаёт актуальные агрегированные показатели в формате, совместимом с Prometheus: как минимум количество клиентов по уровням риска и денежную оценку.
7. **Расширяемость.** Новые признаки и коэффициенты можно добавить без существенной переработки решения, путём минимального редактирования кодовой базы.
8. **Docker.** Решение описано и запускается через Docker Compose.
9. **Аутентификация.** Вход по логину и паролю защищает панель и API с данными клиентов и настройками. OIDC дополнительная функция на усмотрение команды.

## Критерии приёмки

**Без выполнения этих условий решение не принимается.**

### Часть 1: что должно работать

- **Запуск и данные.** Жюри запускает приложение по README. Решение использует тестовый набор данных, предоставленный выше, по усмотрению команды расширенный для наглядности. Результат работы должен быть динамическим и меняться в зависимости от исходных данных, а не быть прописан заранее.
- **Панель и рейтинг.** Видны score, уровни риска и причины. Работают сортировки по основным параметрам в обе стороны.
- **Коэффициенты и обновление.** Изменение коэффициента через панель вызывает пересчёт без reload. Настройки сохраняются после перезапуска; обновление данных также отражается автоматически.
- **Денежная оценка.** Есть актуальная сумма, понятное объяснение её смысла и учёт стоимости услуг, балансов и риска.

### Часть 2: метрики, доступ, передача

- **Метрики.** `/metrics` доступен сборщику, содержит измеренные данные и согласован с главными показателями решения (денежная оценка, риск-скор).
- **Доступ.** Без аутентификации нельзя получить доступ к решению.
- **Передача решения.** Предоставлены исходный код, Compose-файл, инструкция запуска, краткое описание модели и архитектуры, способ добавления нового признака.

## Обязательные эндпоинты API

Ниже перечислены эндпоинты из исходного задания.

### Авторизация

| HTTP-метод | Эндпоинт | Назначение |
|---|---|---|
| POST | `/api/v1/auth/login` | Вход по логину и паролю |
| GET | `/api/v1/auth/me` | Получение текущего пользователя |
| POST | `/api/v1/auth/logout` | Завершение текущей сессии |

### Решение

| HTTP-метод | Эндпоинт | Назначение |
|---|---|---|
| GET | `/api/v1/customers` | Получение списка клиентов с оценками риска; фильтрация и сортировка рейтинга |
| GET | `/api/v1/customers/{id}` | Подробная оценка клиента, его услуг, признаков риска и объяснений |
| GET | `/api/v1/analytics/summary` | Сводные показатели риска и денежной оценки потенциальных потерь |
| GET | `/api/v1/model/settings` | Действующие настройки и коэффициенты модели |
| PATCH | `/api/v1/model/settings` | Изменение настроек модели с автоматическим пересчётом результатов |
| PUT | `/api/v1/source/snapshot` | Загрузка или полная замена снимка исходных данных с автоматическим пересчётом |
| GET | `/metrics` | Агрегированные метрики в формате Prometheus |
| GET | `/api/v1/docs` | Swagger-документация |

Дополнительные фичи дозволяется реализовывать с произвольными эндпоинтами.

К решению обязательно должна быть приложена OpenAPI-спецификация в формате `.yml` или `.json`, а также обязательно должен присутствовать Swagger-эндпоинт с рабочей документацией.
