# Визуальная среда программирования: Java Blueprints

**AXENIX · 48-часовой хакатон · Case Brief**

Кейс на стыке анализа кода, визуального моделирования и автоматической проверки поведения.

---

## Задача кейса

Команда создаёт веб-инструмент, который понимает программу и как код, и как граф, помогает улучшить её и доказывает сохранение результата.

**Схема:** Java-монолит (≈1000 строк Java-кода в одном монолите) → разобрать → визуальная модель → изменить → улучшенное решение.

### Ключевой контракт

После любых преобразований автоматические тесты подтверждают, что поведение программы сохранилось.

---

## Концепт веб-интерфейса

На слайде показан макет интерфейса «Визуальная среда программирования»:

- **Проект:** дерево файлов (`Main.java`, `OrderService.java`, `Validator.java`, `Order.java`, `User.java`, `Constants.java`).
- **Блоки:** переменная, условие, цикл, метод, операция, возврат.
- **Граф:** визуальная блок-схема метода `processOrders`, связанная с кодом.
- **Анализ:** проблемы (длинный метод, дублирование логики, вложенность O(n²)), рекомендации и метрики.
- **Сложность:** текущая O(n²), после оптимизации O(n log n), ожидаемое ускорение до 5.2x.
- **Консоль и тесты:** лог выполнения и результаты тестов (12 из 12 пройдены, поведение совпадает).

Кнопки верхней панели: импорт Java, экспорт Java, оптимизировать, запуск, дебаг.

## Диагностика дефектов и Big O

Пример на слайде: вложенный цикл по элементам, который повторно обрабатывает одинаковые пары.

- **Дефект:** повторная обработка одинаковых пар.
- **Риск:** рост времени при увеличении входа.
- **Рекомендация:** индексировать элементы по `id`.

Что видит участник:

- строку кода и узел графа;
- объяснение найденной проблемы;
- оценку сложности метода или фрагмента;
- вариант исправления с ожидаемым эффектом.

**Диагноз должен быть проверяемым, а не только красивым.**

## Оптимизация и декомпозиция монолита

1. **До:** `Main.java` (≈1000 строк): парсинг, анализ, оптимизация, вывод.
2. **При необходимости:** автоматически выделить ответственности.
3. **После:** `Parser.java`, `Analyzer.java`, `Optimizer.java`, `Main.java`.

**Quality gate:** сборка + автоматические тесты = поведение сохранено.

## Обязательная поддержка Java

Разделы 1–4 обязательны для всех команд. Полный перечень конструкций задаёт технический документ кейса.

### 1. Язык и `java.lang`

- пользовательские классы и интерфейсы;
- примитивы, обёртки, массивы;
- арифметика, логика, сравнение, приведение;
- `if/else`, `switch`, циклы, `break`/`continue`/`return`;
- методы, конструкторы, поля, `static`;
- `try`/`catch`/`finally` и `throw`;
- `Object`, `String`, `Math`, `System` и другие базовые классы.

### 2. Консольный ввод-вывод

- `System.in`, `System.out`, `System.err`;
- `Scanner` и `Formatter`;
- `String.format` и `printf`;
- `StandardCharsets` для корректной работы с кириллицей.

### 3. Коллекции `java.util`

- `Collection` и `Iterable`;
- `List`, `Set`, `Map`;
- `ArrayList`, `LinkedList`, `HashSet`, `TreeSet`, `HashMap`, `TreeMap`;
- `Iterator`, `Collections`, `Arrays`, `Comparator`, `Optional`;
- `List.of`, `Set.of`, `Map.of`.

### 4. Исключения

- проверяемые и непроверяемые;
- `throws` и обязательный `catch`;
- собственные исключения через наследование;
- ключевые типы из `java.lang`, `java.util` и `java.io`.

## Расширенный уровень и границы кейса

### Бонусные возможности

Повышают ценность решения, но не заменяют обязательную базу:

- `record` и `enum`;
- дженерики;
- лямбды и `java.util.function`;
- Stream API и `Collectors`.

### Вне рамок

Не требуются и не оцениваются:

- многопоточность и `java.util.concurrent`;
- рефлексия;
- файловые операции и `java.nio.file`;
- сетевое взаимодействие;
- работа со временем и `java.time`.

## Правила разработки и тестовые задачи

### ИИ и библиотеки

ИИ и библиотеки разрешены свободно. Команды могут выбирать модели, фреймворки, парсеры, графовые и UI-библиотеки без искусственных ограничений со стороны кейса. Оценивается работающее решение и качество результата.

### Подготовка тестовых монолитов

Организаторы вручную формируют набор монолитов, используя ИИ как инструмент. Каждый пример проверяется до выдачи участникам.

Процесс: сценарии и конструкции Java → ИИ помогает сгенерировать код → ручная проверка организаторами.

## Финальная демонстрация и оценивание

### Сценарий демо

Показать полный путь на одном примере: загрузка, визуализация, изменение, генерация Java, запуск и сравнение поведения.

Шаги: монолит → граф → диагноз → улучшение → тесты.

### Проект рамки оценки

- поддержка обязательного Java-scope;
- сохранение поведения;
- полезность диагностики и оптимизации;
- понятность интерфейса;
- качество реализации и демо.

Вес и шкалу критериев организаторы утверждают отдельно.

## Сдача решения

Проект минимального комплекта:

1. **Исходный код:** репозиторий и инструкция запуска.
2. **Веб-демо:** ссылка или воспроизводимая сборка.
3. **Проверка поведения:** автотесты и результат их запуска.
4. **Описание решения:** архитектура, поддержанный scope и ограничения.

Организаторам подтвердить формат сдачи и дедлайн до старта хакатона.

**Результат должен воспроизводить полный путь Java ↔ граф и завершаться автоматической проверкой поведения.**
