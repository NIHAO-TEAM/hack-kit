# Задачи удержания: взять клиента в работу (сервер и контракт)

## Зачем

Сейчас сервис только показывает, кому нужно внимание. Маркетолог не может отметить, что клиентом уже занимаются, кто и до какого срока, и записать контакт. Отметка «в работе» есть в решении (`docs/decision/01_solution.md`, строка «Маркетолог»; слой 3 в `03_verdict.md`, правка 10), но не сделана. Критерий «бизнес-польза»: сервис помогает выполнить работу, а не только читать оценку. Это основа следующих изменений: карточка, экран «Задачи», статус в очереди, наблюдение результата.

## Что меняется

- Задача удержания: клиент, ответственный (логин сотрудника), статус, срок, заметка, история событий. Статусы: «В работе» `in_work`, «Связались» `contacted`, «Отложено» `postponed`, «Закрыто» `closed` (итог: `renewed` «продлил», `refused` «отказался», `no_answer` «не ответил», `not_needed` «не нужно»).
- На клиента — не больше одной открытой задачи. Повтор «взять в работу» не создаёт вторую: ответ 409 с текущей задачей.
- Параллельная правка: в `PATCH` передаётся `version`. Устаревшая версия — 409 «задачу уже изменил <логин>», данные не меняются.
- При взятии запоминается исходное состояние: время модели и снимка, скор, уровень, ожидаемая потеря, главное действие и его эффект, баланс и по услугам — статус, автопродление, срок. Для наблюдения результата (изменение `retention-outcome`).
- Задачи живут отдельно от снимка: новая загрузка снимка их не стирает. Клиент пропал из снимка или у того же ID другой email — задача помечена `customerMissing`, к другому клиенту не привязывается.
- Эндпоинты:
  - `POST /api/v1/customers/{id}/task` — взять в работу (срок по умолчанию — завтра 18:00 МСК, ответственный — текущий пользователь);
  - `GET /api/v1/tasks` — список с фильтрами: статус, ответственный (`me`), просроченные;
  - `GET /api/v1/tasks/{taskId}` — задача с историей;
  - `PATCH /api/v1/tasks/{taskId}` — статус, ответственный, срок, заметка, итог;
  - `POST /api/v1/tasks/{taskId}/events` — записать контакт (канал: почта, телефон, мессенджер, другое) или заметку;
  - `GET /api/v1/tasks/assignees` — кому можно назначить.
- `GET /customers` и `GET /customers/{id}`: краткая задача в строке и карточке (`task`: id, статус, ответственный, срок, просрочена). Новый фильтр `GET /customers?task=none|open|mine`.
- Права на сервере: создавать и менять — маркетолог, `jury`, администратор; аналитик — только чтение. Без сессии — 401, чужая роль — 403.
- Каждое изменение задачи — в журнал действий (`audit`) и событие SSE `tasks`: открытые экраны обновляются без перезагрузки.

Вне изменения:
- Экраны — изменения `retention-task-card`, `retention-tasks-screen`, `retention-queue-status`.
- Сравнение с биллингом после контакта — `retention-outcome` (здесь только исходное состояние).
- Отправка в Telegram и почту — нет (нужен токен бота; напоминания пока внутри сервиса).
- Деньги и скор не меняются: задача — запись о работе, а не данные биллинга.

## Затронутые части

- backend: новый модуль `internal/retention` (задачи, история, права), миграция, `analytics` (поле `task` и фильтр в списке и карточке), `auth/permissions.go` (новые операции), `audit`, SSE
- frontend: только сгенерированные типы `schema.gen.ts`
- контракт `api/openapi.yaml`: да, только добавления (новые пути, поле `task`, параметр `task`)
- защищённые пути: да — `api/openapi.yaml`; причина: новые эндпоинты задач удержания
- зависит от: нет
