# Сборка по профилю (PGO) и предел памяти рантайма

## Зачем

Владелец 24.10: «да» на дешёвые правки скорости Go (ADR-0004, п. 6; ADR-0009). После #146 у нас есть `pprof` и бенчмарки пересчёта. Go 1.21+ умеет собирать бинарь по профилю CPU (PGO): компилятор встраивает горячие функции; обычно это несколько процентов CPU без правки кода. Предел памяти `GOMEMLIMIT` сглаживает сборку мусора на пиках (пересчёт 100k выделяет ≈ 843 МБ за прогон, `docs/load/2026-10-24-recalc-bench.md`).

## Что меняется

- Профиль `backend/cmd/api/default.pgo` снимается с `BenchmarkRecalc100k` и прогона потока событий (`go test -cpuprofile`, затем `go tool pprof -proto` для слияния); `go build` подхватывает `default.pgo` сам (`-pgo=auto`).
- `Dockerfile` (корень): сборка с `-pgo=auto` явно; в README — как обновить профиль.
- `GOMEMLIMIT` в Helm (`values.yaml`: 80 % лимита памяти контейнера) и в Compose; `GOGC` не трогаем без замера.
- Бенчмарки до и после PGO (`BenchmarkRecalc100k`, `BenchmarkRecalc10k`, список клиентов): `benchstat` — в `docs/load/2026-10-24-pgo.md`. Если выигрыша нет или он в пределах шума — так и пишем и оставляем только `GOMEMLIMIT`.

Вне изменения:
- Код модулей и формулы.

## Затронутые части

- backend: `cmd/api/default.pgo`, `Dockerfile`
- frontend: нет
- контракт `api/openapi.yaml`: нет
- защищённые пути: `deploy/helm/churn/values.yaml`, `deploy/docker-compose.prod.yml` (`GOMEMLIMIT` — по причине выше)
- зависит от: нет
