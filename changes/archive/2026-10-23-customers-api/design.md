# Дизайн: рейтинг и карточка

## Подход

- Данные — `Engine.Latest()`: результат `risk.Score` и снимок, на котором он посчитан. Если `Latest` не отдаёт снимок (email, баланс, пополнено) — добавить его в результат отдельным файлом `internal/analytics/latest.go` и одной строкой в `engine.go`; иначе «Найдено по ходу».
- Фильтр и сортировка — в памяти, стабильно (`sort.SliceStable`).
- Поля — строго по схемам контракта `CustomerRow`, `CustomerDetail`; деньги — центы `int64`; тексты причин — из `risk`.

## Допущения

- [ПРЕДПОЛОЖЕНО] `q` — подстрока email без учёта регистра.
- [НАДЕЮСЬ] Сортировка 100k строк ≤ 50 мс (замер в `load-k6`).

## Решения по ходу

- `Engine.Latest()` отдаёт только `risk.Result`, а email и деньги лежат в снимке. `analytics` не может импортировать `risk` (depguard), поэтому сервер собирает `analytics.Portfolio` (`app/portfolio.go`) из результата и снимка, пары берёт по `DataVersion`; `analytics` читает его через интерфейс `Feed`. Вместо `latest.go` из «Подхода».
- Контракт не хватало полей, которые требует `proposal.md` (причина, действие, окно спасения, «к биллингу», `version`, оценка по услугам). Добавлены только необязательные поля и схемы `ActionBrief`, `ServiceRisk`; обязательным стало лишь `version` в ответах (ответ сервера, ломающего клиента нет). Решение по правилу 3.
- `score` и `newScore` — в процентах 0..100, как в модели и эталоне (`risk.Score`); в контракте было «0..1» — исправлено описание, тип не менялся.
- Состояние «потерян» и «нет оценки» — значения `level`; `score = null`.
- `q` ищет по подстроке email без учёта регистра и по подстроке ID (контракт говорит «email или id»).
- Сортировка стабильная, при равенстве — по ID по возрастанию; «нет оценки»/«потерян» внизу при любой сортировке и направлении.
- Окно спасения: `expiresAt` — срок ближайшей услуги `prolong_wait`, `deleteAt` = `expiresAt` + 5 дней (`docs/case.md`).
- `apitest.New` теперь запускает воркер пересчёта; `app.Routes`/`app.New` получили параметр `feed` (nil — клиенты отвечают 503).
