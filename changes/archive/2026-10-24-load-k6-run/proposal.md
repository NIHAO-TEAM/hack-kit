# Настоящие замеры нагрузки в README

## Зачем

Шкала «Продукт и стабильность» и вердикт дебатов: пересчёт после `PATCH /model/settings` на 100k ≤ 1 с, `PUT /source/snapshot` на 100k ≤ 30 с. Сценарии k6 есть (`docs/load/k6/`, изменение `load-k6`), но **ни одного числа нет**: в `docs/load/README.md` написано «Прогон не выполнен» (у исполнителя не было Docker и k6). Жюри смотрит README — пустая таблица хуже, чем её отсутствие.

## Что меняется

- Workflow `.github/workflows/deploy-load.yml` (`workflow_dispatch` и `pull_request` по путям `docs/load/**`, `.github/workflows/deploy-load.yml`): на раннере GitHub поднимает стенд Compose, загружает снимок 100k клиентов, гоняет `snapshot.js`, `recalc.js`, `read.js`, публикует итог k6 в summary запуска и артефактом.
- Лёгкий прогон только чтения по проду (`read.js`, не больше 5 VU, 30 с, учётка `jury` из секрета `E2E_JURY_PASSWORD`) — отдельный job, только по `workflow_dispatch`.
- Числа первого зелёного прогона — в `docs/load/YYYY-MM-DD-load-100k.md` и таблицу `docs/load/README.md` (железо раннера, команда, p95, RPS, ошибки), ссылка из `README.md`.

Вне изменения:
- `snapshot.js` и `recalc.js` по проду — **нет**: они меняют данные прода.
- Оптимизация кода под цели — нет; не уложились — честно пишем число и вывод, оптимизация отдельным изменением.

## Затронутые части

- backend: нет (только если стенд не поднимается — исправление найденного)
- frontend: нет
- контракт `api/openapi.yaml`: нет
- защищённые пути: да — новый `.github/workflows/deploy-load.yml` (исполнителю разрешены новые `deploy*.yml`); причина: прогон нужен Docker и k6, их нет в среде исполнителя
- зависит от: нет
