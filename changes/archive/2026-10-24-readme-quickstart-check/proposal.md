# Жюри запускает по README: проверка буквально по тексту README на чистом раннере

## Зачем

Первый критерий приёмки (`docs/case.md`): «Жюри запускает приложение по README». Без этого решение не принимается. `Demo e2e` поднимает стенд через `docker compose up`, но своими шагами, а не тем, что написано в README; README при этом переписывается (#149). Если в README останется устаревшая команда, переменная или путь, жюри застрянет, а ни один прогон этого не заметит.

## Что меняется

- Новый workflow `.github/workflows/deploy-readme-check.yml` (после выката на `main` и вручную; не гейт слияния): чистый раннер, клон, шаги раздела «Запуск» README выполняются так, как написаны (скрипт берёт блок кода из README между метками `<!-- quickstart:start -->` и `<!-- quickstart:end -->`); пароли — случайные, подставляются вместо подсказки «задайте в .env».
- Затем — раздел «Что проверить за минуту» и таблица обязательных эндпоинтов кейса: `/healthz`, `/`, `/api/v1/docs`, вход `POST /api/v1/auth/login`, `GET /auth/me`, `/customers` (сортировки по ID, email, балансу, пополнениям в обе стороны), `/customers/{id}`, `/analytics/summary`, `GET/PATCH /model/settings`, `PUT /source/snapshot`, `/metrics` (по токену), `logout`; без входа — `401` на путях с данными.
- Проверка, что настройки модели переживают перезапуск (`docker compose restart app`).
- Метки `quickstart` в README добавляются вокруг существующего блока запуска; текст README не меняется.
- Итог — таблица в `$GITHUB_STEP_SUMMARY`.

Вне изменения:
- `Demo e2e`, гейты слияния.
