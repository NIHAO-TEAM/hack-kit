# Дизайн: очередь удержания

## Подход

- `entities/customer` — типы из `schema.gen.ts`, `customersQuery(params)` с ключом `['customers', params]`; `entities/summary` — `['summary']`.
- Сортировка и фильтр — параметры URL (TanStack Router search), запрос на сервер; фронт не пересортировывает.
- Тема и компоненты — ADR-0002 и `design-tokens` (`RescueWindow`, `Money`, `Countdown`, `LevelBadge`). Пять состояний экрана — `shared/ui/states`. Моки MSW — свой файл в `src/mocks/` и одна строка регистрации в конце списка обработчиков. Ключи запросов начинаются с корня из `live-updates`.

## Фронт

- Макет: доски C холста. Состояния: загрузка (скелет таблицы), пусто («сегодня некого спасать»), ошибка, нет связи, нет прав.
- Роль: все вошедшие.

## Решения по ходу

- **Слайсы `widgets/queue-table` и `entities/summary` не созданы.** `steiger` (`fsd/insignificant-slice`) падает на слайсе с одной ссылкой, а гейт ослаблять нельзя. Таблица лежит в `pages/queue/ui`, запрос сводки — в `pages/queue/api`. Когда сводку возьмёт вторая страница, запрос выносится в `entities/summary`.
- **Моки регистрируются в начале списка**, а не в конце: в `handlers.ts` уже есть `/customers` и `/analytics/summary`, MSW берёт первый подходящий. Одна строка `...queueHandlers`.
- **Поля строки очереди.** Первая версия добавляла в `CustomerRow` свои `rescueExpiresAt`, `toBilling`. Пока шло ревью, влился `customers-api` (#54) с `expiresAt`, `deleteAt`, `billing`, `topAction: ActionBrief` и скором в процентах 0..100. Влитый контракт главнее: контракт в этом PR не меняется, экран и моки переведены на имена и единицы из `main` (правило 3).
- Ссылка на карточку — `/queue/<id>` через `router.navigate({ href })`: маршрут `_app.queue.$id` появится в `customer-card-screen`.
- Полоса «удалит биллинг» берёт клиентов первой страницы (`limit=200`) и отбирает тех, у кого идут 5 дней ожидания, по времени стенда `asOf` из сводки. Сроки и деньги считает сервер.
- Первый клик по заголовку: числа — по убыванию, ID и email — по возрастанию; повторный меняет направление.
