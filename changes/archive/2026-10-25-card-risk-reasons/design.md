# Дизайн: причины риска по услугам вместо формулы

## Подход

- Новая функция в `entities/customer-detail`: `riskReasons(serviceRisks, services)` → список услуг с `lossCents > 0` по убыванию `lossCents`; у каждой — `share = lossCents / Σ lossCents` и причины: `features` с `contribution > 0` по убыванию вклада, текст — `reason` с сервера (если пуст — `featureTitle(id)`), сила по доле вклада в сумме вкладов услуги: ≥ 40 % — «сильная», ≥ 15 % — «заметная», иначе «слабая» [ПРЕДПОЛОЖЕНО, пороги на глаз; подписать в коде].
- `FeaturesCard` → `RiskReasonsCard` «Причины риска»: по услуге — строка «название · N € под угрозой» с полосой доли, ниже список причин с силой. Числа доли процентом не пишем — полоса.
- `serviceRisks` пуст (оценки нет) — причины клиента из `features` одним списком без группировки; нет действующих причин — «Явных причин риска нет».
- Внизу — ссылка «Как считается риск» → `/about`.
- `ServiceRiskPanel`: убрать строку `service-formula`.
- `formulaText` удалить из `entities/customer-detail`, если больше нигде не используется, вместе с тестом.

## Отброшенные варианты

| Вариант | Почему нет |
|---|---|
| Свернуть формулу под «Как посчитано» | Эксперт: «лучше убрать или добавить причины» — свёрнутая формула остаётся вычислением в UI |
| Причины клиента одним списком | Эксперт: «по конкретным услугам… какая услуга какой вес даёт, что именно плохого» |
| Проценты вклада у причин | Снова «вычисления»; маркетолог читает на глаз — хватает силы словом и полосы |

## Допущения

- [ПРОВЕРЕНО] Формула выводится в двух местах: `FeaturesCard.tsx`, `ServiceRiskPanel.tsx`.
- [ПРОВЕРЕНО] `ServiceRisk` в контракте: `serviceId`, `lossCents`, `features[]` с `reason` (`api/openapi.yaml`, схемы `ServiceRisk`, `Feature`).
- [ПРЕДПОЛОЖЕНО] Пороги силы 40 % / 15 %.

## Фронт (если задет)

- Роль и право: все, кто видит карточку.
