# Дизайн: задачи удержания (сервер)

## Подход

1. Миграция: `retention_tasks` (id, customer_id, customer_email, status, outcome, assignee, due_at, note, version, baseline jsonb, created_by, created_at, updated_at, closed_at) и `retention_task_events` (id, task_id, at, actor, kind, channel, text, data jsonb). Частичный уникальный индекс: одна открытая задача на `customer_id` (`WHERE status <> 'closed'`). Внешнего ключа на таблицы снимка нет: снимок заменяется целиком.
2. Модуль `internal/retention`: сервис + HTTP по образцу `audit`. Создание в транзакции, гонку двух «взять» решает уникальный индекс: второй получает 409 с задачей первого.
3. `PATCH` с `version`: `UPDATE … WHERE id = $1 AND version = $2`; 0 строк — 409 с текущей задачей и логином того, кто изменил последним. Переходы: из любого открытого в любой; из `closed` — нельзя (взять заново — новая задача). `closed` требует `outcome`. `postponed` требует нового `dueAt`.
4. Связь с клиентом: при чтении задача сверяется с текущим снимком по `customer_id` и `customer_email`. Нет клиента или email другой — `customerMissing: true`, в списке клиентов такая задача не показывается.
5. `baseline` пишется при создании из текущего результата модели: `asOf`, версия пересчёта, скор, уровень, `expectedLossCents`, главное действие (ключ, эффект), `balance`, по услугам `{id, status, autoprolong, expiresAt}`.
6. `GET /customers`: `task` в строке берётся одним запросом открытых задач на страницу. Фильтр `task=none|open|mine` применяется до сортировки и страниц, `total` считается после фильтра.
7. События SSE: `event: tasks` с `{type, taskId, customerId}` после каждой записи. Журнал: `task.create`, `task.update`, `task.event` (без email клиента и текста заметки — только id и поля, как в `audit`).
8. Права: новая группа доступа «работа с клиентом» — `marketer`, `jury`, `admin`; чтение — любая роль.

## Допущения

- [ПРЕДПОЛОЖЕНО] Время задач — реальные часы сервера (это работа людей), а не время модели. Срок по умолчанию — завтра 18:00 МСК; просрочена — `dueAt < now`.
- [ПРЕДПОЛОЖЕНО] Назначить можно только пользователя с ролью `marketer`, `jury` или `admin` (`GET /tasks/assignees`).
- [ПРЕДПОЛОЖЕНО] Заметка и текст контакта — до 2000 символов, пустой текст контакта допустим (канал обязателен).
- [ПРЕДПОЛОЖЕНО] Клиент без оценки и потерянный тоже можно взять в работу: решение маркетолога.

## Риски

- `openapi.yaml` и `schema.gen.ts` параллельно правят `billing-queue-split`, `queue-csv-export`, `contract-error-codes`: при конфликте — перегенерировать после слияния `main`, руками сгенерированное не сливать.
- Инварианты «маршруты = спека» и «401 без входа» должны остаться зелёными: каждый новый путь — в `permissions.go` и в контракте.

## Решения по ходу

- Канал контакта «почта» в контракте называется `mail`, а не `email`: значение `email` меняло имена Go-констант сортировки клиентов (`gen.Email`, `gen.Id` …) и ломало чужой код. Так же действие журнала для событий задачи — `taskRecorded`, а не `taskEvent` (совпадало с типом `TaskEvent`). Критерии не затронуты.
- Контакт и заметка не меняют `version` задачи (только `updated_at`): параллельная запись заметок не должна ломать правку статуса.
- Закрытая задача: правка и запись в историю — 409 с текущим состоянием; взять клиента заново — новая задача.
- [ПРОВЕРЕНО] oapi-codegen v2 (из go.mod): при совпадении значений enum разных схем имена констант получают префикс типа — отсюда решения выше.
- В `.golangci.yml` добавлено правило изоляции модуля `retention` (как у остальных модулей).
