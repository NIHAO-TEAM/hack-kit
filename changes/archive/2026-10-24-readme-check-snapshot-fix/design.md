# Дизайн: починить проверку приёма снимка в README

## Подход

1. Поднять стенд по README локально (или через `workflow_dispatch`) и вызвать `PUT /api/v1/source/snapshot` с телом из `scripts/readme-quickstart.sh` вручную; записать код и тело ответа.
2. По ответу: `401/403` — токен: проверить, задаётся ли `SOURCE_TOKEN` в `.env` и что сказано в README (раздел «Запуск локально», таблица переменных); `400` — тело снимка не проходит `Validate` (текст ошибки покажет поле); `5xx` — ошибка сервера, описать и чинить в отдельной задаче.
3. Скрипт: функция `check` при падении печатает `HTTP <код>` и первые 300 символов тела ответа; перед печатью вырезаются значения токенов и паролей.
4. Привести тело снимка к схеме (`api/openapi.yaml`, `Snapshot`) и к текущим правилам проверки (например, `amount` в 0..1000); добавить в README одну строку, как задать `SOURCE_TOKEN`, если её нет.
5. Прогнать проверку через `workflow_dispatch` дважды подряд.

## Допущения

- [ПРЕДПОЛОЖЕНО] Остальные проверки скрипта зелёные из-за независимости от приёма снимка; после правки они остаются зелёными.

## Риски

- Скрипт печатает тело ответа: убедиться, что в ответах `PUT` нет секретов (ожидается только сообщение об ошибке).

## Решения по ходу

- Docker в среде нет, поэтому ручной вызов стенда заменён прогоном `source.Validate` на теле из скрипта: без `performedAt` — ошибка, с ним — пусто. [ПРОВЕРЕНО] Выбрано: исправить тело в скрипте (меньше всего риска), сервер не трогать.
- Задачи 3.1–3.2 (два прогона `workflow_dispatch`, `main` после слияния) в среде не выполнить — проверит CI.
