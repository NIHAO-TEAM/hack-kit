# Дизайн: пересчёт конвейером

## Подход

1. Сначала профиль: бенчмарк `BenchmarkRecalc100k` и `pprof` (cpu, alloc) на текущем коде; в «Найдено по ходу» записать, где время (выделения, блокировки, сортировка), и оптимизировать только это.
2. Пул воркеров: канал пачек (по 256–1 024 клиента, размер подобрать бенчмарком), `N = GOMAXPROCS` воркеров, результат пачки пишется в свой срез по индексу, без мьютекса; сборка сводки после `WaitGroup`.
3. Отмена: `Recalc` держит `cancel` текущего прогона под мьютексом; новое событие вызывает `cancel()` и запускает следующий прогон; воркеры проверяют `ctx.Err()` между пачками. Публикация результата — только если прогон дошёл до конца и его версия актуальна (сравнение версий снимка и настроек).
4. Результат расчёта не меняется: тест сверяет итог нового конвейера с последовательным расчётом на наборе организаторов и на синтетических 10k, побайтно.
5. `sync.Pool` — только для буферов, которые профиль назвал горячими; без него, если выигрыша нет.
6. pprof: служебный маршрут за токеном метрик (`METRICS_TOKEN`), не в Swagger, роль пользователя его не открывает; тест на `401/403` без токена.
7. Гонки: все тесты пакета проходят с `-race`.

## Допущения

- [ПРЕДПОЛОЖЕНО] Цель «пересчёт 100k ≤ 1 с» на 4 vCPU раннера остаётся целью; результат пишется как есть, даже если не достигнут.
- [ПРЕДПОЛОЖЕНО] Отмена не должна оставлять частичный результат: публикуется только завершённый прогон.

## Риски

- Гонки данных между воркерами и чтением: проверять `-race`.
- Бесконечная отмена при потоке событий (2–3 тысячи в секунду): отмена должна склеиваться (debounce на уровне `dirty`), иначе пересчёт не успеет завершиться; тест с потоком из `events-stream-emulator` или собственный.
