# Дизайн: очередь по причине

## Подход

1. В модели чтения: `byFeature map[string][]int` — позиции клиентов с ненулевым вкладом признака, отсортированные по потере по причине.
2. Параметр `reason` проверяется по реестру признаков; неизвестный — `400` с перечнем допустимых.
3. Фронт: значение фильтра в URL (`?reason=susp`), чтобы ссылку со «Сводки» можно было открыть в новой вкладке.

## Риски

- Конфликт `openapi.yaml` с другими изменениями — зависимость от `read-model-index`.

## Решения по ходу

- Потеря клиента по причине считается тем же `risk.AllocateLoss`, что «Где теряем деньги», при сборке портфеля в `app` (поле `Customer.Loss`); сумма по причине совпадает со сводкой (тест на данных организаторов: `susp` — 2 клиента, 184 419 ц).
- Список допустимых причин приходит в `Portfolio.Reasons` из `app` (модуль `analytics` не импортирует `risk`, depguard); известная причина без клиентов даёт пустую страницу, неизвестная — `400` с перечнем.
- Без `sort` при заданном `reason` порядок — по потере по причине; явный `sort` остаётся как есть. Курсор различает эти случаи (`reason:<признак>` в поле сортировки).
- Добавлено необязательное поле `reasonLossCents` строки списка (только с `reason`) — добавление контракта; `reason` принимает и `export.csv`.
- На фронте «по потере по причине» — значение `reasonLoss` в адресе очереди; серверу `sort` при нём не передаётся. По умолчанию с `?reason=` очередь идёт по нему.
- [ПРЕДПОЛОЖЕНО] В CSV новых колонок нет, фильтр сужает строки; колонку потери по причине не добавляли, чтобы не менять формат файла.
