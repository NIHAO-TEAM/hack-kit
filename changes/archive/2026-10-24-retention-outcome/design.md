# Дизайн: наблюдения после взятия в работу

## Подход

1. Хук после успешного пересчёта (там же, где сейчас уходит SSE `recalculated`): для открытых задач — сравнить `baseline` с текущими данными клиента. Сравнение — чистая функция `observe(baseline, current) []Observation`, без БД.
2. Дубли не пишутся: у наблюдения ключ `kind + serviceId + значение` (например, новый `expiresAt`), уникальный индекс по `(task_id, key)` или проверка перед записью.
3. Пополнение — рост `balance` относительно `baseline.balance` (последнего записанного значения, чтобы не писать то же пополнение дважды).
4. После записи — SSE `tasks` с `customerId`.
5. Фронт: вид события `observed` в истории и отдельный раздел «После взятия в работу»; подписи — в `entities/retention-task`.

## Допущения

- [ПРЕДПОЛОЖЕНО] Изменение скора пишется только при смене уровня риска — иначе история шумит на каждой правке коэффициента.
- [ПРЕДПОЛОЖЕНО] Правка коэффициентов модели аналитиком тоже меняет скор; наблюдение «скор изменился» помечается «после изменения модели», если пересчёт вызван `PATCH /model/settings`. **Не реализовано, см. «Решения по ходу».**
- [ПРЕДПОЛОЖЕНО] Сравнение по времени модели снимка (`asOf`), а не по реальным часам.

## Риски

- Пересчёт на 100k клиентов (`load-k6-run`): сравнение только для открытых задач, их единицы — время пересчёта не растёт заметно; проверить замером.

## Решения по ходу

- Наблюдатель (`retention.Service.StartObserver`) слушает тему `recalculated` в отдельной горутине и запускается из `app.Recalc.Start`: сам пересчёт он не замедляет, по построению. Сравнение 100 открытых задач — 0,29 мс (`BenchmarkObserve100`), плюс один запрос открытых задач.
- Ключ наблюдения — колонка `obs_key` в `retention_task_events` с уникальным индексом `(task_id, obs_key)`; запись `INSERT … ON CONFLICT DO NOTHING` с проверкой статуса задачи в самом запросе (закрытая между чтением и записью не получит наблюдения).
- Последний записанный баланс берётся из ключей `balance:<центы>`; до первого пополнения — баланс из `baseline`.
- Для колонки «Что изменилось» в `RetentionTask` добавлено поле `lastObservation` (только добавление в контракте); в списке задач истории нет, поэтому подпись приходит отдельным полем.
- Автор наблюдений в истории — `system`.
- Пометка «после изменения модели» не реализована: пересчёт не знает причину запуска. Смена уровня риска после правки коэффициентов запишется как обычное наблюдение о скоре; подпись раздела причинности не утверждает.
- Если услуги уже нет в снимке, в тексте наблюдения её номер («Услуга 7 удалена»): в `baseline` имени услуги нет. Услуга со статусом `deleted` или `blocked` в снимке — с именем.
- `Observe` пишет наблюдения по одному `INSERT` на запись; для единиц открытых задач этого достаточно, при сотнях задач стоит собрать пачкой.
