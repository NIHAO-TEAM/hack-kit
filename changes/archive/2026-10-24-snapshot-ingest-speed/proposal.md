# Загрузка снимка 100k: сначала замер по этапам, потом ускорение

## Зачем

`docs/load/2026-10-23-load-100k.md`: `PUT /source/snapshot` на 100k клиентов (331 МБ) — 42,5 / 45,1 / 45,1 с при цели ≤ 30 с. На 10 000 клиентов то же занимает 0,7 с (`2026-10-23-large-snapshot.md`): рост в 10 раз по данным дал рост в 60 раз по времени, значит, дело не только в объёме. Где именно уходит время, неизвестно: запрос включает разбор JSON (потоковый, `ParseSnapshot`), проверку (`Validate`), копирование трёх таблиц (`CopyFrom` с проверками CHECK, внешними ключами и индексами) и подтяжку последовательностей. Кроме того, в замере три загрузки идут подряд, а второй и третий `TRUNCATE` ждут блокировку, пока читатель пересчёта держит транзакцию `REPEATABLE READ` над теми же таблицами (пересчёт после предыдущего снимка идёт ~15 с). Это гипотеза, а не вывод.

## Что меняется

- Сервер замеряет и пишет в лог этапы загрузки: чтение и разбор тела, проверка, ожидание блокировки, `TRUNCATE`, копирование каждой таблицы, последовательности, фиксация. Метрика `churn_snapshot_ingest_stage_seconds{stage}`.
- По замеру исправляется самый большой этап, один за раз, с замером до и после. Кандидаты, от самого вероятного: ожидание блокировки из-за читателя пересчёта; построчная сборка `[][]any` для `CopyFrom` вместо потокового источника; проверки и индексы при копировании (порядок: копирование без `serviceId`-индекса, индекс после — только если замер покажет, что это главное и схема остаётся 1:1 с организаторами).
- Итог записывается в `docs/load/` с честным числом.

Вне изменения:
- Формат снимка, проверки данных, ответы API, схема таблиц организаторов — без изменений. Если ускорение требует правки таблиц, оно в это изменение не входит: исполнитель записывает в «Найдено по ходу» и ждёт решения человека.
- Цель 30 с не меняется; не достигнута — пишется в замере.

## Найдено по ходу
- Гипотеза о блокировке из-за читателя пересчёта не подтвердилась (`lock`/`truncate` ≈ 0 при загрузке во время пересчёта). Главные этапы: `copy_transactions` (≈ 8–10 с), `parse` (6–9 с).
- Цифры по этапам на стенде GitHub не получены: `deploy-load.yml` не выводит лог приложения, а правка существующего workflow запрещена исполнителю. Предложение человеку: выводить этапы из `/metrics` в summary.
- Нелинейность 10× данных → ≈ 27× времени не объяснена.
