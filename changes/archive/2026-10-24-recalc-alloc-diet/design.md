# Дизайн: пересчёт без лишних выделений

## Подход

1. `go test -bench Recalc100k -benchmem -memprofile` на `main`; топ-10 мест выделений в «Найдено по ходу».
2. Править только места из топа, по одному, с `benchstat` после каждого; правка без выигрыша откатывается.
3. Типичные приёмы: `scratch` на воркер (`[]float64` вкладов, `[]string` id признаков) с `s = s[:0]`; `strings.Builder` из пула для причин; отказ от `fmt.Sprintf` в горячем пути (причины форматировать, когда их читают).
4. Равенство результатов: golden, `-tags parity` на 10k, тест равенства конвейера и последовательного расчёта (#146).

## Допущения

- [ПРЕДПОЛОЖЕНО] Ленивая строка причины допустима, если API отдаёт тот же текст; иначе причины форматируются как сейчас.

## Риски

- Гонки на общих буферах: буферы строго на воркер; `-race`.

## Решения по ходу

- Задача 2.1 говорила о буфере признаков и вкладов «на воркер». `Features` и `Services` попадают в итог (`Result`), переиспользовать их нельзя: взяты точные ёмкости (`make(..., 0, n)`), а нулевая длина признаков сохранена как `nil`, как раньше. Буфер воркера (`scratch`) заведён там, где данные не уходят в итог, — для копии данных клиента в `actionResults`.
- Ленивые строки причин для карточки не вводились: это меняет `Feature.Eval` и формат результата, а ответ API обязан остаться тем же. Вместо этого причины не считаются там, где результат отбрасывается (`ServiceCtx.NoReason` в пересчёте после действия), а форматирование не использует `fmt.Sprintf` [ПРЕДПОЛОЖЕНО: выигрыша 3,5× хватает для цели «3+»].
- Индекс транзакций снимка переиспользуется в `scoreOne`, только если действие вернуло тот же срез транзакций; иначе индекс строится заново, как раньше (контракт `Action.Apply` транзакции менять позволяет).
- Индексы `svcByOwner`/`txByService` и раньше строились раз на прогон, не на клиента; 2.4 сократил число выделений на них (один массив на индекс).
- `govulncheck` из `make check` не запустился: нет доступа к vuln.go.dev. Остальное (gofmt, vet, golangci-lint, `go test -race`) зелёное.
