# Дизайн: дашборд «Внутри сервиса»

## Подход

1. Сначала список метрик, которые реально отдаёт `/metrics` на `main` (поднять сервер локально, `curl /metrics`); в «Найдено по ходу» — что есть, чего нет.
2. Дашборд — JSON рядом с `churn.json`, подхватывается тем же provisioning; uid постоянный.
3. HTTP-гистограмма: `churn_http_request_duration_seconds{route,method,code}`, `route` — шаблон из маршрутизатора; бакеты 5 мс…5 с.
4. Проверка: тест, что JSON дашборда разбирается и каждый запрос PromQL ссылается на метрику из списка, который отдаёт сервер в тесте (или помечен «нет данных до слияния»).
5. Скриншот дашборда во время `Deploy load` — в `docs/load/` (если владелец запустит замер).

## Допущения

- [ПРЕДПОЛОЖЕНО] Удаление панелей задач из Grafana следует из ADR-0004 п. 1 («интерфейса нет»); метрики задач на сервере остаются.

## Риски

- Кардинальность меток HTTP: только шаблон маршрута, без id и query.

## Решения по ходу

- [ПРЕДПОЛОЖЕНО] Квантиль p99 пауз GC рантайм Go не отдаёт (`go_gc_duration_seconds` — квантили 0, 0.25, 0.5, 0.75, 1). Панель показывает максимум и p75 вместо p99.
- Панели про метрики, которых нет на `main` (отмены пересчёта, события/с, потери шины), названы «… (нет данных до слияния)»; тест требует пометку, пока метрики нет в коде, и требует снять её, когда метрика появится.
- Имена метрик события — предположение: `churn_recalc_cancelled_total`, `churn_events_published_total`, `churn_events_dropped_total`; если `recalc-concurrency` и `events-bus-fanout` назовут иначе, поправить выражения.
- Метка `route` — полный шаблон mux вместе с методом (`GET /api/v1/customers/{id}`), метка `method` оставлена как в design.md.
- Тест соответствия метрикам: `go_*`/`process_*` из живого `/metrics`, `churn_*` — по строковым литералам в `backend/internal`, потому что без базы часть метрик в `/metrics` не видна.
