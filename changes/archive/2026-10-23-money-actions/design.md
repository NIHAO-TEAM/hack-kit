# Дизайн: действия с ценой

## Подход

- Реализации интерфейса `Action` из `risk-core` (`RegisterAction`), по файлу на действие: `action_topup.go`, `action_autoprolong.go`, `action_billing.go`.
- `Action { ID() string; Applies(CustomerCtx) bool; Apply(Snapshot, accountID) Snapshot; Title(CustomerCtx) string }`. Эффект считает ядро одинаково для всех действий: `Score` на снимке, где изменён только этот клиент (копия его аккаунта и услуг), разница `ExpectedLossCents` клиента; скор и уровень после.
- Пополнение: `balance += need − have` (центы, целые). Автопродление: `autoProlong = true` у всех живых услуг клиента с `noauto > 0` (как в оракуле).
- «К биллингу» — не меняет данные: `Applies` по правилу, эффект 0, тип `to_billing`, в очереди такой клиент помечается, а не продвигается.
- Стоимость: пересчёт одного клиента — O(его услуг); для 100k клиентов по 2 действия — 200k пересчётов клиента, укладывается в цель «пересчёт ≤ 1 с» [НАДЕЮСЬ — замер в `load-k6`].
- Golden `actions_golden_test.go` сравнивает поле `actions`: `type`, `lossDeltaCents` точно, `scoreBefore`/`scoreAfter` до 0,01, `levelAfter`.

## Отброшенные варианты

| Вариант | Почему нет |
|---|---|
| Эффект по отдельной упрощённой формуле | разойдётся с моделью; жюри спросит «откуда цифра» (`01b.md`, раздел 6) |
| Пересчёт всего снимка на каждое действие | O(N²) на 100k клиентов |

## Допущения

- [ПРОВЕРЕНО] Эталон: №9 «пополнить на 529,84 €» → −1 067,48 €; №1 «автопродление» → −365,29 €, скор 56,02 → 41,57 (`r2_B.md`, golden).
- [ПРЕДПОЛОЖЕНО] Действия считаются только для `high` и `medium`.

## Риски

- Если ядро не даёт пересчитать одного клиента без всего снимка — запись в «Найдено по ходу», временно пересчёт всего снимка, замер.

## Решения по ходу

- Эталон (`testdata/golden`) считает действия всем клиентам с положительным `funds`/`noauto`, в том числе уровня `low` (клиент 6), а не только `high` и `medium`. Эталон главнее допущения выше: действия считаются для всех клиентов в состоянии `scored`.
- `Apply(s, accountID)` не получает настройки, а «нужно» для пополнения зависит от `priceBasis`. Выбрано: необязательный интерфейс `settingsAction` с `ApplyWith(s, accountID, st)`; ядро вызывает его, если он есть. Реестр и интерфейс `Action` не ломаются.
- «К биллингу» нужны не живые услуги клиента, а в `CustomerCtx` их не было: добавлено поле `Services` (все услуги аккаунта).
- Сортировка действий по эффекту (правило 9) сделана в `actionResults` ядра: одно место для всех действий.
- Тег «к биллингу» оракул не считает, поэтому в golden-тесте он исключён из сверки; поведение держит `TestToBillingApplies`.
- [ПРЕДПОЛОЖЕНО] Сумма пополнения проверяется по заголовку действия («Пополнить баланс на 529,84 €»): в `ActionResult` нет поля суммы, ядро под это не расширялось.
