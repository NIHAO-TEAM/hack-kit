# Дизайн: приём событий извне

## Подход

1. Разбор потоком (`bufio.Scanner` с пределом строки 64 КБ для NDJSON, `json.Decoder` для массива); предел тела `http.MaxBytesReader` 2 МБ → `413`.
2. Проверка каждой строки до постановки в канал; ошибки — в `rejected` с номером строки, остальные принимаются (частичный приём строк с ошибкой формата; «всё или ничего» — только при перегрузке канала).
3. Идемпотентность: таблица `source_event_ids(event_id text primary key, seen_at timestamptz)`; вставка в той же транзакции пачки (`ON CONFLICT DO NOTHING` → `duplicate`); чистка старше 24 ч фоновой задачей.
4. Постановка в канал писателя `event-ingest-delta` с таймаутом 1 с; не влезло — откат постановки этого запроса (события запроса ставятся одним сообщением-пачкой, поэтому откат прост).

## Допущения

- [ПРЕДПОЛОЖЕНО] Формат события — как у эмулятора (`StreamEvent`), чтобы один конвейер; если у aéza другой формат — адаптер на входе.
- [ПРЕДПОЛОЖЕНО] Если `tx.Commit` id упадёт уже после постановки в очередь, события будут применены, а id не занят: повтор применит их второй раз. Для событий «новый баланс/статус» результат тот же, вреда нет (как и потеря принятого в очередь при остановке).

## Риски

- Пересечение с `burst-live-panel` в `internal/source` — разные файлы, слияние `main`.

## Решения по ходу

- **Окно id и ответ `duplicate`.** Ответ должен сказать про дубли сразу, а применение асинхронное, поэтому id занимаются синхронно: `INSERT … ON CONFLICT DO NOTHING RETURNING` в транзакции запроса, транзакция держится до постановки событий в очередь. Очередь не приняла за 1 с — откат, id свободны, повтор после `503` не считается дублем. Вместо «вставки в той же транзакции пачки» (она пишется потом и ответа не ждёт).
- **Свой писатель, не канал эмулятора.** Писатель `event-ingest-delta` создаётся на прогон эмулятора. Для приёма извне поднят второй экземпляр того же `eventWriter` на весь срок процесса: тот же пакетный путь записи и та же метрика пачек, но очередь на 10 000 событий (вмещает самый большой запрос целиком; нужно для «всё или ничего»). Постановка запроса — `offerAll`: ждёт место на все события, не дольше 1 с, иначе не ставит ничего.
- **Проверка существования счёта и услуги — при записи.** Снимок может смениться между проверкой и записью, поэтому приём проверяет значения (диапазон суммы, известный статус, нужные поля по виду события), а существование решает запрос: ни одной строки — событие считается неприменённым (метрика `churn_ingest_api_events_total{result="failed"}`). В `rejected` такие события не попадают: ответ 202 приходит раньше записи.
- **Формат.** Поля события — как у `StreamEvent` плюс `eventId`. Неизвестные поля игнорируются. Номер в `rejected.line` — физическая строка NDJSON (пустые строки номер не сдвигают) или позиция элемента массива с 1.
- **Нет снимка — `400`.** Событиям применяться не к чему; сид приём сам не создаёт (в отличие от прогона эмулятора).
- **Чистка окна.** Фоновой задачи нет: запрос, принятый не раньше часа после прошлой чистки, удаляет id старше 24 часов. Без горутин и без часов на уровне процесса.
- **Тип `kind` и `status` в контракте — строки.** Перечисление дало бы константы, совпадающие со статусами услуги (`prolong_wait`), и сгенерированный код сломал бы чужие пакеты; значения проверяет сервер.

## Допущения (дополнение)

- [ПРЕДПОЛОЖЕНО] Потеря при остановке процесса: события, принятые в очередь, но не записанные до `SIGTERM`, теряются, а их id уже в окне. Закрытие очереди при остановке (`graceful-shutdown`) не подключено: изменение трогает только `internal/source`. Источник при сомнении шлёт пачку с новыми `eventId`.
- [ПРЕДПОЛОЖЕНО] 2 МБ на запрос ограничивают тело, а не распакованное число событий; 5 000 событий ≈ 400 байт на событие.
