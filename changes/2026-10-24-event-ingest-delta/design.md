# Дизайн: точечный приём событий пачками

## Подход

1. Сначала замер на текущем коде: поток 2 500 событий на снимке 10 000 клиентов (`snapgen`), события/с и p95 применения — в «Найдено по ходу».
2. Новый файл `internal/source/ingest.go`: `type ingester struct{ in chan StreamEvent; ... }`, одна горутина-писатель. `runStream` кладёт событие в канал (блокируется при полном буфере — это обратное давление) вместо `commitStep`.
3. Писатель: `select` с таймером 5 мс; пачка → `pool.BeginTx` → `pgx.Batch` из точечных `UPDATE`/`INSERT` → `UPDATE source_meta SET version = version + 1` (или как версия хранится сейчас — проверить) → `Commit` → `bus.Publish(TopicChanged, …)`.
4. Ошибка события внутри пачки: проверка до записи (по снимку в памяти или `UPDATE … RETURNING`, 0 строк — событие `failed`). Ошибка БД на пачке — повтор пачки один раз, затем все события пачки `failed` и лог.
5. Снимок в памяти для генерации следующих событий обновляется тем же `applyStreamEvent` локально, без чтения из БД.
6. Порядок блокировок таблиц — как у `Reader.Load` (accounts, services, transactions), см. ошибку из `docs/load/2026-10-24-snapshot-stages.md`.
7. Аудит: одна запись на прогон, а не на событие (проверить, как сейчас; не терять запись о запуске).

## Допущения

- [ПРЕДПОЛОЖЕНО] Окно пачки 5 мс и размер 1 000 — стартовые значения, подбираются замером.
- [ПРЕДПОЛОЖЕНО] Цель 1 000 событий/с на 100k при полном пересчёте после пачек достижима только вместе со склейкой пересчётов (она уже есть, `dirty`); задержка «событие → очередь» до `incremental-recalc` будет равна полному пересчёту — пишем как есть.

## Риски

- `snapshot-stream-parse` правит приём снимка в том же пакете: `replace` и `snapshot.go` здесь не трогаем, конфликт по `service.go` — слиянием `main`.
