# Сортировка очереди по ID, email, балансу и пополнениям — по всему списку

## Зачем

Кейс, обязательный функционал 2: «Обязательна сортировка по ID, email, балансу и общей сумме пополнений в обе стороны». Аудит 24.10 (проверено по коду `analytics/customers.go:67-85`): компаратор сначала безусловно ставит `lost`/`unscored` после оценённых, а между собой сравнивает их по ID по возрастанию до выбранного столбца. На данных организаторов `sort=id&order=asc` даёт `1,4,5,6,9,10,2,3,7,8`, а `level=lost&sort=id&order=desc` — `2,3,7,8`. `TestListCustomersSorts` закрепляет это разбиение и порядок хвоста не проверяет.

Решение человека (сессия 24.10): по ID/email/балансу/пополнениям сортировать весь список; неоценённых держать внизу только при сортировке по скору и ожидаемой потере.

## Что меняется

- `sort` = `id`, `email`, `balance`, `totalReplenished`: весь отфильтрованный список упорядочен по полю в выбранном направлении, независимо от уровня; при равенстве — ID по возрастанию.
- `sort` = `score`, `expectedLoss` (и по умолчанию): `lost`/`unscored` внизу, как сейчас; между собой — по ID.
- Фильтр `level=lost` с любым столбцом соблюдает направление.
- Фронт очереди: если он группирует или досортировывает строки на клиенте — убрать, порядок только с сервера (проверить).

Вне изменения:
- Набор полей сортировки и контракт — не меняются.
- Пагинация — изменение `queue-pagination`.

## Затронутые части

- backend: `internal/analytics/customers.go`, `internal/app/portfolio_test.go`
- frontend: `pages/queue` — только если найдена клиентская досортировка (гипотеза, проверить)
- контракт `api/openapi.yaml`: нет (описание параметра `sort` уточнить нельзя без правки контракта — не трогаем)
- защищённые пути: нет
- зависит от: нет
