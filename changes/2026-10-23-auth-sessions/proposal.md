# Вход по логину и паролю, сессии и права ролей

## Зачем

Кейс: «Вход по логину и паролю защищает панель и API с данными клиентов и настройками»; приёмка: «Без аутентификации нельзя получить доступ к решению» (`docs/case.md`). Эксперт: эндпоинты нужны им для тестов — значит, жюри должно пройти весь API одним логином и паролем (P0 дебатов, `docs/decision/03_verdict.md`, правка 1).

## Что меняется

- `POST /api/v1/auth/login` по логину и паролю выдаёт сессию: cookie (HttpOnly, SameSite=Lax, Secure — настройкой) и тот же токен в теле ответа для `Authorization: Bearer`.
- `GET /api/v1/auth/me` — текущий пользователь и роль; `POST /api/v1/auth/logout` завершает сессию.
- Учётки создаются при старте из окружения: администратор (`ADMIN_LOGIN`, `ADMIN_PASSWORD`, через панель не меняется) и демо-учётки `marketer`, `analyst`, `jury` (пароли `DEMO_*_PASSWORD`; без пароля учётка не создаётся). Паролей в репозитории нет.
- Права ролей проверяются на сервере для каждого пути (матрица в `design.md`): маркетолог не меняет модель и данные даже через API; `jury` проходит все пути.
- Без сессии любой путь с данными отвечает `401`; открыты только вход, документация, спека и служебные пути.
- Для запросов с cookie небезопасные методы требуют заголовок `X-CSRF-Token`; запросы с Bearer — нет.
- Повторные неверные попытки входа ограничены по паре логин + IP.
- `/metrics` пускает по токену сборщика (`METRICS_TOKEN`) или по сессии.

Вне изменения:
- Второй фактор (TOTP), FIDO2, OIDC — этап 6 (`keycloak-oidc`); ядро — только пароль (`03_verdict.md`).
- Экран входа — `frontend-shell`.
- Экран и API управления пользователями — не делаем (не требуется кейсом).

## Затронутые части

- backend: `internal/auth` (заполняет заглушку из `churn-foundation`), промежуточный слой прав в `internal/auth`
- frontend: нет
- контракт `api/openapi.yaml`: нет (пути уже в контракте)
- защищённые пути: нет
