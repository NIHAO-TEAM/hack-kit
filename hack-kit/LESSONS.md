# Уроки UMIRHack 2026 (кейс «Флагмана»)

Итог 17.10.2026: 1 — Goden, 2 — «Остаток», 3 — RIMS. SwapOwl и «Запас» (самый широкий по функциям) без призов. Протоколов жюри мы не видели, поэтому выводы ниже сделаны по репозиториям победителей и нашему опыту. Где это гипотеза, так и сказано.

Источники: `VegasYT/goden-hackathon`, `3xfap2/hadashadfsj`, `TrolDrol/UMIRHack2026AutumnFlagman`, наш `immxrtalbeast/SwapOwl` и наши правила в `per/ai-private/.ai/`.

## 1. Что было у всех трёх победителей и не было у нас

| Признак | Goden | «Остаток» | RIMS | SwapOwl |
|---|---|---|---|---|
| Компании и точки | да, ADR-013 | несколько ресторанов у владельца | предприятие и склады | одна точка |
| Роли | владелец, управляющий, приёмщик, повар, официант | шеф, управляющий, повар, кладовщик, официант | сотрудники, гость, поставщик | admin и viewer, на стенде вход выключен |
| Отдельный экран на каждую роль | да | экран кухни, зал, QR-меню | три портала | частично: «Для зала», mini-app |
| Внешний участник процесса | доставка «Мигом» | касса и сайт по ключу | поставщик со своим порталом | адаптер iiko на эмуляторе |
| Видимая инженерия | Kafka, Keycloak, Grafana, Loki | таблица нагрузки, 2 724 запросов/с | Grafana, проверки сбоев | сторожа и e2e, со стороны не видны |
| Короткое видео | «Goden за 47 секунд» | — | — | 6 минут рассказа |

**Вывод.** Победители показали знакомый ресторанный продукт: вошёл под ролью и видишь свою работу. Мы показали умный движок учёта: прогноз с измеренной точностью, деньги под риском, лестницу спасения. Ни у кого из призёров точности прогноза нет. Значит, жюри её либо не взвешивало, либо мы не смогли её объяснить.

## 2. Где мы потеряли время

1. **Сменили визуальный язык на четвёртый день** (решение H от 12.10, переход на стиль линейки Swap). Переделывали готовые экраны, а роли и точки так и не появились.
2. **Процесс шёл за замечаниями.** Поправки эксперта, отчёты критика, срочные PR. Около 200 PR за неделю, и в README в итоге первой стоит таблица «что сказал эксперт». План продукта на всю неделю не держали.
3. **Тратились на работу с агентами.** Рутины Jira, четыре исполнителя на общих лимитах Pro, планировщик, раздача задач. Это обслуживание, а не продукт.
4. **Фронт без каркаса.** Нет роутера, нет слоя данных (TanStack Query), нет ESLint и Prettier, нет витрины компонентов. Каждый экран писали по-своему, а исправляли через e2e.
5. **На стенде выключили вход** ради удобства демо. Выглядит как прототип.
6. **Ставку делали на глубину,** а показ шёл слайдами: 12 слайдов на 6 минут.

## 3. Что берём у победителей

### Goden: процесс и архитектура

- **Спецификация до кода (OpenSpec).** На каждое изменение — папка с `proposal.md`, `design.md`, `tasks.md` и `specs/`. После слияния папка уходит в архив, сценарии — в общие `specs/`. В `config.yaml` правила для агента: «не выдавай предположение за решение», «утверждение о коде сначала проверь», «вне изменения: …». → у нас `template/changes/` и скиллы `change-*`.
- **ADR на каждое архитектурное решение** (у них 14). → `template/docs/adr/`.
- **AGENTS.md по частям репозитория.** Агента запускают из папки части, чтобы подгрузились только её правила. `CLAUDE.md` в одну строку: `@AGENTS.md`. → так же.
- **Скиллы в `.agents/skills/`, `.claude/skills` — ссылка на эту папку.** Один набор работает в Claude и Codex. Имена с префиксом части: `frontend-…`, `backend-…`. → так же, плюс скрипт ссылок для Windows (у Goden с ними были проблемы).
- **Контракт первым.** Правится `openapi.yaml`, по нему генерируется сервер (ogen) и типы для фронта (`openapi-typescript`). Сгенерированный код коммитится, руками не правится.
- **Границы проверяет линтер.** depguard на Go-модули, steiger на слои фронта. «Нарушение исправляется в коде, а не исключением в конфиге».
- **Тестовая обвязка:** `apitest.New(t)` (весь API тем же конструктором, что в проде), эталонные JSON событий, `testing/synctest` и фейковые часы, тест свойств под нагрузкой.
- **Фронт: дизайн-система как скилл.** Смысл цветов, запреты (hex в компонентах, лишние варианты типографики запрещены типами), каталог компонентов `shared/ui`, порядок «куда писать стиль», витрина `/dev/ui`, автотест контраста WCAG AA, тёмная тема с первого дня, размеры по способу ввода (`pointer: coarse`).
- **Фронт: скилл тестирования.** Тест только на поведение, искать элементы как пользователь (`getByRole`), общие хелперы, известные подводные камни.
- **Фронт: анти-slop.** Проверка, что дизайнерский выбор сделан под продукт, а не по привычке. Плюс скилл `interface-design`: сначала намерение (кто, какое действие, какое ощущение), потом сигнатура продукта.
- **Макеты на холсте** (claude.ai artifact) и `CHECKLIST.md` фронта, привязанный к изменениям OpenSpec.

### «Остаток»: показ и проверяемость

- Отдельный проект нагрузочных тестов и сводки замеров в `docs/load/`. Честная оговорка «порядок величин, не обещание».
- 50 одновременных заказов на 5 порций: ровно 5 прошли. Один такой сценарий убеждает лучше любого слайда.
- Демо-ресторан в один клик и вход под каждой ролью.
- Бот с собственными тестами без сети: Telegram и API подставные.
- CI на любой ветке.

### RIMS: контракт и демо без бэкенда

- Типы API зафиксированы версиями (`contracts/core-v2.ts.txt`), скрипт `check-contract` в CI сверяет с ними фронт.
- MSW-моки и пакет `demo-api`: фронт работает без backend, параллельная разработка не блокируется.
- `check-built-css`: проверка, что в собранном CSS есть палитра и шрифт (ловит потерю стилей при сборке).
- Отдельный CI-процесс прогоняет все порталы в браузере на настоящей базе.

## 4. Что оставляем своё (это было сильнее, чем у всех)

- **Дебаты по решению в день 0:** два независимых решения, три агента, два раунда (`ai-private/.ai/debate-prompt.md`).
- **Якорная шкала по критериям жюри** (3, 6 и 9 баллов) и **критик глазами жюри,** который видит только кейс, шкалу и стенд.
- **Сторожа-инварианты** на настоящем PostgreSQL, менять их могут только люди. Защищённые пути: слияние только после явного «да».
- **AI-ревью каждого PR в CI** по чек-листу с правилом доказательства.
- **e2e на живом стенде,** сброс стенда в демо-состояние, симулированное время.
- **Детальная спецификация экранов:** шкала срочности одним модулем, пять состояний экрана, форматы чисел и времени. По глубине она лучше дизайн-системы Goden, но к ней не было ни витрины, ни линтеров.
- **Цифры эффекта с живого стенда** в презентации.

## 5. Фронт и дизайн: разбор подробно

| | SwapOwl | Goden | Что берём в шаблон |
|---|---|---|---|
| Направление | Сменили на 4-й день, подражание стилю линейки Swap «Флагмана» с оговоркой «концепт» | Выбрано в начале, держится скиллом: «направление не пересматривают на каждом экране» | Выбор один раз в день 0 из трёх вариантов на холсте, ADR-0002 (`frontend-design-direction`) |
| Спецификация | Очень подробная: токены, шкала срочности, пять состояний, форматы | Дизайн-система как скилл + каталог компонентов `shared/ui` | Наша глубина состояний и форматов + их каталог и порядок «куда писать стиль» (`frontend-design-system`, `frontend-screens`) |
| Проверка | Глазами и e2e | Витрина `/dev/ui`, автотест контраста, ограничение вариантов типами, steiger, stylelint, `pnpm check` | Всё это + скриншоты по матрице и axe (`frontend-design-review`, `scripts/screenshots.mjs`) |
| Макеты | Один UI-kit и макет, «если макета нет — вопрос» | Холст с макетом каждой страницы, ссылка в чек-листе | Макет каждого экрана на холсте, все состояния, две темы, две ширины — до вёрстки |
| Тёмная тема | Сначала запрет, потом добавили (#177–#198) | С первого дня, скрипт ранней установки | С первого дня |
| Плотность | По ширине | По способу ввода (`pointer: coarse`) и по ширине | По способу ввода и ширине |
| Стек | Mantine, свой hash-роутинг, без слоя данных, без ESLint/Prettier | MUI, TanStack Router + Query + Form, FSD, ESLint, Prettier, Stylelint, steiger, React Compiler | Mantine (знаем), TanStack Router + Query, FSD-lite, полный набор линтеров (`frontend/AGENTS.md`) |
| Тесты | 60 тестов, Playwright Firefox | Философия «тест только на поведение», хелперы `renderApp`, `mockGet`, `FakeEventSource` | Их философия и хелперы + наш Playwright Firefox (`frontend-testing`) |
| Демо без бэкенда | Нет | Нет | Да, как у RIMS: MSW-моки, `pnpm dev:mock` |
| Анти-slop | Не было | Скилл `no-ai-design-slop` | Свой сжатый чек-лист и тест удаления |

**Неприятная находка.** Наш стиль SwapOwl — моноширинный капс в заголовках, «миллиметровка» на фоне, рукописные пометки — почти дословно совпадает с кластером «фальшивая солидность» из анти-slop каталога Goden («monospaced micro-labels, decorative grid»). Нам он казался сигнатурой, со стороны мог читаться как шаблон. Правило в шаблоне: сигнатура живёт в одном-двух местах экрана и выведена из мира продукта, а не из чужого бренда.

## 6. Что больше не делаем

- Не меняем визуальный язык после дня 0.
- Не выключаем вход на стенде: вместо этого кнопки «Войти как повар / управляющий / официант».
- Не ведём процесс в Jira. Задача = PR с папкой `changes/`, согласование = метка, разговор = комментарии в PR ([AGENTS-SETUP.md](AGENTS-SETUP.md)).
- Не даём агенту-планировщику самому запускать исполнителей: запуск — метка `go:*` от человека.
- Не кладём в README таблицу ответов эксперту первой строкой. README начинается с продукта.
- Не прячем процесс с агентами: Goden выложил весь свой и занял первое место.
- Не делаем 12 слайдов: 5–6 слайдов и видео до минуты.
