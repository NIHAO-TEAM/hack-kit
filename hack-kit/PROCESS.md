# Процесс

Рассчитан на хакатон длиной 2–7 дней (основной план — на 48 часов, раздел 6): команда из 3–5 человек, у каждого свой агент (Claude Code или Codex). Для обычного проекта он тот же, меняется только темп.

## 1. Роли

| Роль | Кто | Что делает |
|---|---|---|
| Владелец продукта | человек | Принимает решения: что в объёме, какое направление дизайна, что показываем. Ставит `go:<id>`, говорит «да» на защищённые пути |
| Владелец дизайна | человек, можно тот же | Выбирает направление в день 0, принимает макеты экранов, смотрит скриншоты в PR |
| Пахан (ведущий агент) | Opus 5.5, effort high: локальная сессия владельца | Открывает черновики PR с предложениями, держит ADR, следит за доской, ведёт план этапов и вопросы к сессиям с экспертами (`docs/plan.md`, `docs/experts/`). Код пишет редко (`.github/agents/lead.md`) |
| Исполнители | Sonnet 5.5, effort medium, routine на аккаунте своего человека | По метке `go:<id>` одна сессия ведёт PR до конца: делает изменение, подписывается на события PR, отвечает на ревью, сливает одобренное (`.github/agents/executor.md`) |
| Ревьюер | Sonnet 5.5, effort high, routine с API-триггером (его вызывает CI) | Ревью каждого коммита PR с зелёными тестами по `.github/review-prompt.md` (`.github/agents/reviewer.md`). Раунды и метки считают Actions без модели |
| Критик | Opus 5.5, effort high, ночная routine | Смотрит стенд глазами жюри по `docs/scale.md`, открывает PR с отчётом (`.github/agents/critic.md`) |

Как именно они общаются (PR, метки, префиксы комментариев) и как их настроить — [AGENTS-SETUP.md](AGENTS-SETUP.md).

Исполнителей не больше, чем людей, которые могут смотреть их PR. Четыре агента на общих лимитах — это обслуживание, а не скорость (урок SwapOwl).

## 2. Источники правды

| Что | Где | Кто меняет |
|---|---|---|
| Кейс и критерии жюри дословно | `docs/case.md` | никто после дня 0 |
| Якорная шкала оценки | `docs/scale.md` | владелец продукта |
| Архитектурные и дизайн-решения | `docs/adr/NNNN-*.md` | ведущий агент, принимает человек |
| Текущее поведение системы | `specs/<capability>/spec.md` | только через архив изменения |
| Изменения в работе | `changes/<дата>-<имя>/` | исполнитель своего изменения |
| Контракт API | `api/openapi.yaml` | отдельным изменением с пометкой «контракт» |
| Инварианты | `tests/invariants/` | только люди |
| Правила частей | `AGENTS.md`, `<часть>/AGENTS.md`, скиллы | ведущий агент по согласованию |

Если документы расходятся, прав ADR. Расхождение — повод для отдельного изменения, а не для тихой правки.

## 3. Цикл изменения

```
explore → propose (черновик PR) → человек: go:<id> → apply + archive в том же PR
       → снять черновик → CI: checks → ревью → [review] → [ci] итог принят → правки / слияние
```

1. **explore** (по желанию). Разобраться в вопросе и записать, что проверено, а что предположено. Код не пишем.
2. **propose** (`change-propose`, пахан). Черновик PR с папкой `changes/YYYY-MM-DD-<имя>/`:
   - `proposal.md` — зачем, что меняется, «Вне изменения:», какие части репозитория задеты;
   - `design.md` — как сделать, какие варианты отброшены, ссылки на ADR;
   - `tasks.md` — задачи с чекбоксами, каждая проверяема;
   - `specs/<capability>.md` — сценарии WHEN/THEN, только наблюдаемое поведение;
   - для фронта — ссылка на макет экрана (обязательно, см. `frontend/AGENTS.md`).
3. **Человек смотрит предложение** и ставит метку `go:<id>`: одно действие = согласование + назначение + запуск исполнителя. Либо утверждает этап в `docs/plan.md` (слияние PR), и `assign.yml` сам запускает исполнителей на изменения этапа по очереди, пока есть место (`team.md`). Мелочь (опечатка, стиль) идёт обычным PR без предложения.
4. **apply** (`change-apply`, исполнитель). Задачи по порядку в ветке PR, чекбоксы по ходу. Вне объёма — в «Найдено по ходу», не делать.
5. **archive** (`change-archive`) — последним коммитом в том же PR: сценарии в `specs/`, папка в `changes/archive/`, `frontend/CHECKLIST.md`.
6. **Ревью.** Исполнитель снимает черновик, CI гоняет проверки и запрашивает ревью; итог `[review]` принимает `review-post.yml` и дублирует его комментарием бота `[ci] итог ревью принят`, по которому просыпается подписанная сессия исполнителя. До 4 раундов, дальше человек.
7. **Слияние.** APPROVED и зелёный CI: исполнитель сам сливает PR в `main` (squash), без человека. Исключение — PR с меткой `manual-merge` (он трогает правила процесса или сторожей, либо ломает контракт; раздел 5): его сливает человек. Остановить слияние может и метка `needs-human`.

Размер изменения — то, что делается за 2–6 часов. Больше — делить.

## 4. Гейты (что проверяет машина)

| Гейт | Чем | Где |
|---|---|---|
| Формат, линт, типы | gofmt, go vet, golangci-lint; tsc, eslint, prettier, stylelint | `make check` / `pnpm check` |
| Границы модулей | depguard (Go), steiger (слои фронта) | там же |
| Контракт | сгенерированный код совпадает с `openapi.yaml`, фронт собран на тех же типах | CI: `generate && git diff --exit-code` |
| Инварианты | `tests/invariants/` на настоящем PostgreSQL | CI на каждый PR |
| Контраст | автотест пар «текст на фоне» ≥ 4,5 : 1 в обеих темах | `pnpm test` |
| Сборка стилей | в собранном CSS есть токены и шрифт | `scripts/check-built-css.mjs` |
| e2e | Playwright (Firefox) на стенде после деплоя | CI после деплоя |
| Ревью | AI-ревью по чек-листу | CI на каждый PR |

Если гейт падает, ошибка в коде. Ослабить гейт можно только отдельным изменением, на которое владелец продукта сказал «да».

## 5. Защищённые пути

`tests/invariants/`, `e2e/`, `deploy/`, `.github/` (workflow-файлы, правила ревью, инструкции агентов), `.agents/` (скиллы), `AGENTS.md`, `CLAUDE.md`, `team.md`, `docs/plan.md`, `api/openapi.yaml` (последний — только через изменение с пометкой «контракт»). Исполнитель трогает их только по причине из `proposal.md`, CI ставит на такие PR метку `protected` — внимание ревьюеру.

Слияние зависит от пути:

- `deploy/` и добавления в `api/openapi.yaml` — как у остальных: после APPROVED сливает исполнитель.
- Ломающая или ослабляющая правка `api/openapi.yaml` (поле стало необязательным или nullable, снята валидация, удалён путь) — CI сравнивает контракт `oasdiff` и ставит `contract-breaking`, дальше `manual-merge`. Решение принимает инструмент, а не ревьюер.
- `tests/invariants/`, `e2e/` — сторожей меняют только люди, поэтому `manual-merge` здесь потока не тормозит, а ловит агента, нарушившего запрет.
- `.github/`, `.agents/`, `AGENTS.md`, `CLAUDE.md`, `team.md`, `docs/plan.md` — это правила самого процесса, агент не должен утверждать собственные правила. Такие PR получают метку `manual-merge` (список — `.github/workflows/manual-merge-paths.txt`), и после APPROVED их сливает человек. Перед слиянием исполнитель проверяет статус `merge-gate` (его ставит `review-post.yml`). С защитой ветки (`hack-kit/AGENTS-SETUP.md`) обычный `gh pr merge` без него не пройдёт; без защиты это держит инструкция исполнителя.

Параллельные исполнители одного этапа: общие правки (контракт, миграции, общие сценарии) — отдельным изменением с `!` в строке этапа, оно сливается первым, остальные `assign.yml` запускает после него (`lead.md`, «Разбивка на этапы»).

Правка сторожей без строки `INVARIANT-CHANGE: …` от человека — 🚨 у ревьюера, такой PR не одобряется.

## 6. План на 48 часов

Время считается от старта хакатона. Агенты работают круглосуточно, люди спят по очереди: ночью работают исполнители, ревьюер и критик, и именно ночью `needs-human` стоит дороже всего. Поэтому перед сном каждый человек разбирает свои `needs-human`, ставит `go:*` на всё готовое и обновляет «Доступен» в `team.md`.

| Часы | Цель | Результат на стенде |
|---|---|---|
| 0–2 | [DAY0.md](DAY0.md), блок 1: кейс дословно в `docs/case.md`, `docs/scale.md`, роли людей из кейса | Согласованная шкала и список ролей |
| 2–4 | Дебаты (`debate`, один раунд, два независимых решения), `docs/adr/0001-solution.md` | Решение: что делаем, что показываем, что не делаем; изюминка с цифрой |
| 4–5 | Направление дизайна (`frontend-design-direction`), `docs/adr/0002-design-direction.md` | Выбранное направление; дальше не пересматривается |
| 5–8 | Каркас: бэкенд и фронт из шаблона, вход под ролями, CI, деплой | Стенд открывается с телефона, вход под каждой ролью, пустые экраны в выбранном стиле |
| 8–20 | Ядро домена и контракт; параллельно экраны главного сценария на моках | Главный сценарий кейса проходит через API и виден в браузере |
| 20–32 | Ночь. Экраны всех ролей и «внешний участник» (поставщик, касса, доставка). Критик около часа 24 | Все роли делают свою работу; первый отчёт критика разобран |
| 32–40 | Изюминка: алгоритм, прогноз или деньги, с цифрой эффекта | Цифра на стенде |
| 40–44 | Нагрузка (`docs/load/`), анти-slop по всем экранам, сброс стенда в демо-состояние | Замеры в `docs/load/`, чек-лист пройден |
| 44–48 | Фриз: только исправления. Видео до 60 секунд, слайды, репетиция демо 3 раза | Демо по `docs/demo-script.md` три раза подряд без сбоев |

Отличия от недельного плана:

- Каркас берётся из шаблона, а не создаётся. Дебаты и выбор дизайна нельзя растягивать: не уложились в срок — берём лучший из готовых вариантов, обсуждение закрыто.
- Один раунд дебатов вместо двух; ADR только на решения, которые трудно отменить.
- Размер изменения 1–3 часа, а не 2–6: за 48 часов их набирается 30–50, длинные не успеют пройти раунды ревью.
- Критик запускается раз в 8 часов (расписание его routine `0 */8 * * *`), а не раз в сутки.
- До старта: routines созданы и проверены, секреты и метки настроены, тестовый PR прошёл цепочку целиком ([AGENTS-SETUP.md](AGENTS-SETUP.md)). В часы хакатона инфраструктуру не настраиваем.

### Если хакатон длиннее: план на 7 дней

| День | Цель дня | Результат на стенде вечером |
|---|---|---|
| 0 (первые 6 ч) | [DAY0.md](DAY0.md): кейс, дебаты, направление дизайна, каркас | Вход под ролями, пустые экраны ролей в выбранном стиле, CI и деплой работают |
| 1 | Ядро домена и контракт: главные сущности, инварианты, сторожа | Главный сценарий кейса проходит через API |
| 2 | Экраны главного сценария для всех ролей | Повар, управляющий, официант делают свою работу в браузере |
| 3 | Второй круг кейса и «внешний участник» (поставщик, касса, доставка) | Сценарий с внешней системой виден вживую |
| 4 | Изюминка: алгоритм, прогноз, деньги | Цифра эффекта на стенде |
| 5 | Показ: нагрузка, мониторинг, бот или мобильная версия, полировка | Замеры в `docs/load/`, Grafana, анти-slop пройден на всех экранах |
| 6 | Фриз: только исправления, видео, слайды, репетиция | Демо по сценарию 3 раза подряд без сбоев |

Ритм суток: ночью критик (routine) открывает PR с отчётом → утром человек просит пахана (локальная сессия) собрать доску и отчёт критика, пахан открывает до 3 черновиков → люди ставят `go:*` → днём исполнители и ревьюер гоняют PR → вечером человек разбирает `needs-human` и меняет «Доступен» в `team.md`. Критик работает с дня 2.

## 7. Показ

- Видео до 60 секунд: главный сценарий от входа до результата.
- 5–6 слайдов: проблема, кто пользователь, сценарий, архитектура одной картинкой, цифры, что дальше.
- Живое демо по `docs/demo-script.md`, у каждого шага есть запасной ход.
- README начинается с продукта и ссылки на стенд, потом запуск, потом архитектура. Таблица соответствия кейсу — ниже.
- Цифры на слайдах берутся только со стенда или из `docs/load/`.

## 8. Агенты: общие правила

- Предположение не выдаём за решение. Неясно и от этого зависит поведение — вопрос человеку. Мелочь — допущение в `design.md`.
- Утверждение о существующем коде сначала проверяем по коду.
- Работаем из папки части (`cd frontend && claude`), чтобы подгрузились её правила.
- Секреты только в `.env` на сервере и в секретах CI. В чат, лог и коммит не печатаем.
- Чужие стенды и репозитории — только чтение.
- Сообщение коммита и PR — по-русски, по делу, с атрибуцией агента, если её требует настройка.
