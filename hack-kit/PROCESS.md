# Процесс

Рассчитан на хакатон длиной 3–7 дней: команда из 3–5 человек, у каждого свой агент (Claude Code или Codex). Для обычного проекта он тот же, меняется только темп.

## 1. Роли

| Роль | Кто | Что делает |
|---|---|---|
| Владелец продукта | человек | Принимает решения: что в объёме, какое направление дизайна, что показываем. Ставит `go:<id>`, говорит «да» на защищённые пути |
| Владелец дизайна | человек, можно тот же | Выбирает направление в день 0, принимает макеты экранов, смотрит скриншоты в PR |
| Пахан (ведущий агент) | Opus 5.5: локальная сессия владельца + утренняя routine | Открывает черновики PR с предложениями, держит ADR, следит за доской, утром отчитывается. Код пишет редко (`.github/agents/lead.md`) |
| Исполнители | Sonnet 5.5, routine на аккаунте своего человека | По метке `go:<id>` одна сессия ведёт PR до конца: делает изменение, подписывается на события PR, отвечает на ревью, сливает одобренное (`.github/agents/executor.md`) |
| Ревьюер | Opus 5.5, routine по метке `review-me` | Ревью каждого коммита PR с зелёными тестами по `.github/review-prompt.md` (`.github/agents/reviewer.md`). Раунды и метки считают Actions без модели |
| Критик | Opus 5.5, ночная routine | Смотрит стенд глазами жюри по `docs/scale.md`, открывает PR с отчётом (`.github/agents/critic.md`) |

Как именно они общаются (PR, метки, префиксы комментариев) и как их настроить — [AGENTS-SETUP.md](AGENTS-SETUP.md).

Исполнителей не больше, чем людей, которые могут смотреть их PR. Четыре агента на общих лимитах — это обслуживание, а не скорость (урок SwapOwl).

## 2. Источники правды

| Что | Где | Кто меняет |
|---|---|---|
| Кейс и критерии жюри дословно | `docs/case.md` | никто после дня 0 |
| Якорная шкала оценки | `docs/scale.md` | владелец продукта |
| Архитектурные и дизайн-решения | `docs/adr/NNNN-*.md` | ведущий агент, принимает человек |
| Текущее поведение системы | `specs/<capability>/spec.md` | только через архив изменения |
| Изменения в работе | `changes/<дата>-<имя>/` | исполнитель своего изменения |
| Контракт API | `api/openapi.yaml` | отдельным изменением с пометкой «контракт» |
| Инварианты | `tests/invariants/` | только люди |
| Правила частей | `AGENTS.md`, `<часть>/AGENTS.md`, скиллы | ведущий агент по согласованию |

Если документы расходятся, прав ADR. Расхождение — повод для отдельного изменения, а не для тихой правки.

## 3. Цикл изменения

```
explore → propose (черновик PR) → человек: go:<id> → apply + archive в том же PR
       → снять черновик → CI: checks ║ ревью → [review] → wake:<id> → правки / слияние
```

1. **explore** (по желанию). Разобраться в вопросе и записать, что проверено, а что предположено. Код не пишем.
2. **propose** (`change-propose`, пахан). Черновик PR с папкой `changes/YYYY-MM-DD-<имя>/`:
   - `proposal.md` — зачем, что меняется, «Вне изменения:», какие части репозитория задеты;
   - `design.md` — как сделать, какие варианты отброшены, ссылки на ADR;
   - `tasks.md` — задачи с чекбоксами, каждая проверяема;
   - `specs/<capability>.md` — сценарии WHEN/THEN, только наблюдаемое поведение;
   - для фронта — ссылка на макет экрана (обязательно, см. `frontend/AGENTS.md`).
3. **Человек смотрит предложение** и ставит метку `go:<id>`: одно действие = согласование + назначение + запуск исполнителя. Мелочь (опечатка, стиль) идёт обычным PR без предложения.
4. **apply** (`change-apply`, исполнитель). Задачи по порядку в ветке PR, чекбоксы по ходу. Вне объёма — в «Найдено по ходу», не делать.
5. **archive** (`change-archive`) — последним коммитом в том же PR: сценарии в `specs/`, папка в `changes/archive/`, `frontend/CHECKLIST.md`.
6. **Ревью.** Исполнитель снимает черновик, CI гоняет проверки и ревью, итог `[review]` будит исполнителя меткой `wake:<id>`. До 4 раундов, дальше человек.
7. **Слияние.** APPROVED и зелёный CI: исполнитель сам сливает PR в `main` (squash), без человека, для любого PR. Остановить может только метка `needs-human`.

Размер изменения — то, что делается за 2–6 часов. Больше — делить.

## 4. Гейты (что проверяет машина)

| Гейт | Чем | Где |
|---|---|---|
| Формат, линт, типы | gofmt, go vet, golangci-lint; tsc, eslint, prettier, stylelint | `make check` / `pnpm check` |
| Границы модулей | depguard (Go), steiger (слои фронта) | там же |
| Контракт | сгенерированный код совпадает с `openapi.yaml`, фронт собран на тех же типах | CI: `generate && git diff --exit-code` |
| Инварианты | `tests/invariants/` на настоящем PostgreSQL | CI на каждый PR |
| Контраст | автотест пар «текст на фоне» ≥ 4,5 : 1 в обеих темах | `pnpm test` |
| Сборка стилей | в собранном CSS есть токены и шрифт | `scripts/check-built-css.mjs` |
| e2e | Playwright (Firefox) на стенде после деплоя | CI после деплоя |
| Ревью | AI-ревью по чек-листу | CI на каждый PR |

Если гейт падает, ошибка в коде. Ослабить гейт можно только отдельным изменением, на которое владелец продукта сказал «да».

## 5. Защищённые пути

`tests/invariants/`, `e2e/`, `deploy/`, `.github/` (workflow-файлы, правила ревью, инструкции агентов), `.agents/` (скиллы), `AGENTS.md`, `CLAUDE.md`, `team.md`, `api/openapi.yaml` (последний — только через изменение с пометкой «контракт»). CI ставит на такие PR метку `protected`, сливает их только человек. Строку `INVARIANT-CHANGE: …` в PR пишет человек.

## 6. План по дням (7-дневный хакатон)

| День | Цель дня | Результат на стенде вечером |
|---|---|---|
| 0 (первые 6 ч) | [DAY0.md](DAY0.md): кейс, дебаты, направление дизайна, каркас | Вход под ролями, пустые экраны ролей в выбранном стиле, CI и деплой работают |
| 1 | Ядро домена и контракт: главные сущности, инварианты, сторожа | Главный сценарий кейса проходит через API |
| 2 | Экраны главного сценария для всех ролей | Повар, управляющий, официант делают свою работу в браузере |
| 3 | Второй круг кейса и «внешний участник» (поставщик, касса, доставка) | Сценарий с внешней системой виден вживую |
| 4 | Изюминка: алгоритм, прогноз, деньги | Цифра эффекта на стенде |
| 5 | Показ: нагрузка, мониторинг, бот или мобильная версия, полировка | Замеры в `docs/load/`, Grafana, анти-slop пройден на всех экранах |
| 6 | Фриз: только исправления, видео, слайды, репетиция | Демо по сценарию 3 раза подряд без сбоев |

Ритм суток: ночью критик (routine) открывает PR с отчётом → утром пахан (routine) разбирает доску и отчёт, открывает до 3 черновиков и пишет «[lead] утро» → люди ставят `go:*` → днём исполнители и ревьюер гоняют PR → вечером человек сливает `protected` и меняет «Доступен» в `team.md`. Критик работает с дня 2.

## 7. Показ

- Видео до 60 секунд: главный сценарий от входа до результата.
- 5–6 слайдов: проблема, кто пользователь, сценарий, архитектура одной картинкой, цифры, что дальше.
- Живое демо по `docs/demo-script.md`, у каждого шага есть запасной ход.
- README начинается с продукта и ссылки на стенд, потом запуск, потом архитектура. Таблица соответствия кейсу — ниже.
- Цифры на слайдах берутся только со стенда или из `docs/load/`.

## 8. Агенты: общие правила

- Предположение не выдаём за решение. Неясно и от этого зависит поведение — вопрос человеку. Мелочь — допущение в `design.md`.
- Утверждение о существующем коде сначала проверяем по коду.
- Работаем из папки части (`cd frontend && claude`), чтобы подгрузились её правила.
- Секреты только в `.env` на сервере и в секретах CI. В чат, лог и коммит не печатаем.
- Чужие стенды и репозитории — только чтение.
- Сообщение коммита и PR — по-русски, по делу, с атрибуцией агента, если её требует настройка.
