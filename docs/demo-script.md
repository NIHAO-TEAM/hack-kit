# Демо-сценарий

Из этого файла пишется e2e (`e2e/tests/demo.spec.ts`). Каждый шаг проверяется на стенде после сброса. Цифры — из `docs/decision/03_verdict.md` [ПРОВЕРЕНО прототипом]; после реализации их снимает golden-тест.

## Состояние после сброса

- Время модели `asOf` = 2026-10-19T15:00Z (данные организаторов), пояс отображения — МСК.
- Одна организация. Учётки: `marketer` (маркетолог), `analyst` (аналитик), `jury` (все пути), `secure` (вход через Keycloak с ключом доступа или TOTP, слой 2). Пароли — в материалах сдачи, не в README.
- Данные: 10 аккаунтов организаторов + 5–8 ручных (id от 1001): свежие `prolong_wait` на 1–3 дня до удаления, аккаунт без услуг, низкий риск.
- Цикла «взять в работу», экрана «Задачи», сроков и блока наблюдений в интерфейсе нет (ADR-0004: CRM не делаем). Данные и API задач на сервере остаются для будущей калибровки.
- На данных организаторов: высокие №10, 5, 9; средние №4, 1; низкий №6; потеряны №2, 3, 7, 8. Ожидаемая потеря 3 599,07 €.

## Живое демо (5 минут)

Каждая строка — шаг `test.step` в `e2e/tests/demo.spec.ts` (прогон `Demo e2e`). Названия экранов и кнопок — как в интерфейсе.

| Шаг | Роль | Действие | Что видит жюри | Запасной ход, если не сработало |
|---|---|---|---|---|
| 1. Найти клиента | маркетолог | вход, «Очередь» по ожидаемой потере; переключить на скор | сумма «Ожидаемая потеря за 30 дней» 3 599,07 €; №9 первый по деньгам, №10 — по скору; почему расходятся | скриншоты очереди в слайдах |
| 2. Объяснить | маркетолог | карточка №9: «Признаки риска клиента», блок «Что сделать» (действие, цена, «Снимает потерю», «На каждый €») | потеря №9 3 189,10 € и из чего она; действие «пополнить на 529,84 € — −1 027,49 €» | экран «О модели» |
| 3. Где теряем деньги | маркетолог | «Сводка»: блок «Где теряем деньги» | потеря по причинам, по убыванию, с долями; пометка «не доказанная причинность» | `GET /analytics/summary` через Swagger |
| 4. Изменить коэффициент | аналитик, второе окно | «Модель»: `noauto` 0,55 → 0,85, «Что изменится» (предпросмотр), применить; «О модели» → «Насколько устойчива очередь» | у маркетолога без перезагрузки №1 стал высоким (84,75), потеря 3 805,22 €; таблица устойчивости к сдвигу веса на ±20 % | `PATCH /model/settings` через Swagger под `jury` |
| 5. Изменить данные | аналитик | эмулятор: «включить автопродление №1» (или правка услуги на экране «Источник») | №1 уходит в низкий, потеря снижается на ~375 € | `PUT /source/snapshot` с правленым файлом |

Поток событий | аналитик | «Источник» → «Поток событий»: 2 500 событий, скорость «Без пауз» → «Прогнать 2 500 событий»; в конце «Сбросить» | ход потока, итог прогона и «Согласованность: пересчёт с нуля совпал (разница 0 ¢ …)» | `POST /source/emulator/stream` через Swagger; готовый замер `docs/load/2026-10-24-events-2500.md` |

## Вопросы жюри и ответы

| Вопрос | Ответ одной фразой | Где показать |
|---|---|---|
| Откуда 3 599 €? | Сумма платежей на 30 дней, взвешенная вероятностью срыва; новые клиенты и скидки не входят | карточка, «О модели» |
| Почему не ML? | Истории статусов нет — обучать не на чем; веса экспертные и редактируются | «О модели» |
| `price` у почасовой — за час? | Это настройка `price_basis`; по умолчанию — за период, как в данных | экран «Модель» |
| Почему 89 % у одного клиента? | Так распределены цены в наборе; мы продаём метод — действие с ценой, а не эту долю | очередь |
| Откалибрована ли вероятность? | Нет: скор — оценка риска по экспертным весам, истории оттока в данных нет; калибровка — когда появится история | «О модели», «Ограничения» |
| Это доказанный ROI? | Нет: это пересчёт «клиент выполнил действие полностью»; отклик, стоимость контакта и маржа не учтены | карточка, блок действия |
| Как добавить признак? | Файл признака с регистрацией, правило, оракул, тест и подпись в `featureInfo`; вот изменение в истории репозитория | README, PR |
| Чем это отличается от CRM? | Это не CRM: в интерфейсе нет задач, сроков, контактов и воронки; есть причина риска, потеря в евро и действие с ценой | очередь, карточка |
| Как встать к вам в контур? | `values.yaml`: адрес биллинга, OIDC-issuer, Prometheus | Helm-чарт |
| Почему Go, монолит, без Kafka и Redis? | Ядро в одном процессе: событие доходит до пересчёта без сети; данные — в PostgreSQL. Подробные ответы эксперту — в `docs/pitch.md` | ADR-0009, `docs/pitch.md` |
