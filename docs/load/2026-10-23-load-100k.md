# Замер: 100k клиентов (стенд на раннере GitHub)

Запуск: [https://github.com/NIHAO-TEAM/hack-kit/actions/runs/40039523161](https://github.com/NIHAO-TEAM/hack-kit/actions/runs/40039523161) (workflow `Deploy load`, коммит `pull_request` #90).

## Железо и условия

- Раннер `ubuntu-latest` GitHub Actions (стандартный: 4 vCPU, 16 ГБ). k6 0.54.0, приложение и PostgreSQL 16 на той же машине, Compose.
- Данные: `cases/analizator/generate.py --accounts 100000 --services 300000 --transactions 1000000`, файл 331 МБ, `--seed 42`.
- Команды: см. `.github/workflows/deploy-load.yml` (шаги «k6 snapshot», «k6 read», «k6 recalc»).

> Замер на раннере GitHub. Это порядок величин, а не обещание для боевого сервера.

## Оговорки

- Метрика пересчёта читается после PATCH и могла отражать последний завершённый пересчёт (после загрузки снимка), а не пересчёт от самого PATCH: PATCH отвечает за 2 мс, то есть пересчёт идёт асинхронно. Раздельно точно этого запуск не показал.
- p95 `summary` отдельно не выделен: сценарии k6 различаются тегом, но выгрузка сводки содержит только общий p95.
- Снимок принимался трижды подряд на одну базу; разброс 42–45 с.

## Вывод

На стандартном раннере загрузка снимка 100k занимает около 44 с, список с сортировкой отвечает с p95 1,8 с под 10 VU, пересчёт по метрике сервера около 15 с: все три цели из вердикта дебатов пока не достигнуты, оптимизация — отдельным изменением.
