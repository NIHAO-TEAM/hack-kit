# Замер: приём событий извне по HTTP

Изменение `events-ingest-api`. Вход `POST /api/v1/source/events` принимает пачки событий (NDJSON или JSON-массив, до 5 000 событий и 2 МБ) и ставит их в тот же писатель пачек, что и поток эмулятора (`event-ingest-delta`). Нагрузка идёт по HTTP снаружи процесса, а не изнутри, как у эмулятора.

## Статус: числа не сняты

В среде исполнителя нет ни k6, ни Docker, ни PostgreSQL, поэтому прогона не было. **Цифр в этом отчёте нет и придуманных не будет.** Сценарий готов, прогон ждёт стенда; после него таблица ниже заполняется выводом k6 без округления.

## Сценарий

`docs/load/k6/ingest.js`: пачки по 500 событий `top_up` на постоянной скорости (`constant-arrival-rate`, по умолчанию 10 пачек в секунду = 5 000 событий/с, 60 с), у каждого события свой `eventId`; параллельно 2 читателя очереди клиентов. Пороги: ни одной ошибки (кроме 503 с `Retry-After`), все проверки проходят. Отдельно считаются принятые события, дубли и отклонённые из-за давления пачки (`ingest_batches_shed`).

```sh
# стенд с загруженным снимком (100 000 клиентов), пароль администратора в PASSWORD
k6 run -e BASE_URL=http://localhost:8080 -e PASSWORD=… docs/load/k6/ingest.js
# выше скорость: -e BATCH_RATE=40 -e DURATION=120s
```

## Что проверено без стенда

- Разбор и пределы (5 000 событий, 2 МБ, строка до 64 КБ), построчные ошибки, идемпотентность и «всё или ничего» при полной очереди — модульные тесты `internal/source/events_*_test.go` (очередь писателя без базы, окно `eventId` в памяти).
- Эндпоинт целиком с PostgreSQL — `events_integration_test.go`, прогонит CI (`make test-int`).
