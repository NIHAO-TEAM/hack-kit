# Замер: сверка Go с эталоном на больших снимках

Дифференциальная проверка: `snapgen` → Go (`backend/tools/snapcalc`, тот же `risk.Score`, что у пересчёта, без HTTP и БД) и эталон `tools/oracle/oracle.py --per-customer` → построчное сравнение (`tools/oracle/parity_compare.py`). Эталон под Go не подгонялся.

## Условия

- **Не стенд GitHub.** Контейнер разработки: 4 vCPU Intel Xeon @ 2,30 ГГц, 15 ГБ памяти, Go 1.24.7, Python 3.11.17. Числа сравнимы только по порядку.
- Снимок: `snapgen -accounts N -seed 1`, `asOf` из снимка (2026-10-19T15:00:00Z), настройки по умолчанию.
- Время Go — весь процесс `snapcalc`: чтение и разбор JSON, расчёт, запись. Время эталона — весь процесс `oracle.py`, на одном ядре.
- Сравниваются для каждого клиента: состояние, уровень, скор, ожидаемая потеря, под угрозой и потерянное в центах, набор действий (тип → эффект в центах), лучшее действие. Скор Go и эталона округляют до двух знаков одинаково, поэтому сравнение точное, без допуска. Порядок списка действий не сверяется: Go сортирует по выгоде, эталон отдаёт в фиксированном порядке. Действие `to_billing` эталон не считает, оно исключено (как в `TestActionsGolden`).

## Команды

```
make -C backend parity N=300000 SEED=1      # N клиентов, по умолчанию 10000
PARITY_DIR=/путь make -C backend parity …   # куда класть снимок и результаты
go test -tags parity ./tools/snapcalc/      # быстрый вариант, 10 000 клиентов, из backend/
```

## Результат

| N | Клиентов сверено | Расхождений | Go, с | Эталон, с |
|---|---|---|---|---|
| 10 000 | 10 000 | 0 | 0,3 | 0,5 |
| 100 000 | 100 000 | 0 | 2,8 | 5,7 |
| 300 000 | 300 000 | 0 | 9,3 | 20,5 |

Снимок на 300 000 клиентов — 342 МБ; эталон уложился в память контейнера (15 ГБ), до ограничений раннера не проверялось.

## Что нашли

- Расхождений в числах нет. Единственное расхождение первого запуска — порядок действий в списке (Go по выгоде, эталон фиксированный): это договорённость о сравнении, а не ошибка модели; сверка идёт по набору действий и лучшему действию.
- Проверка ловит ошибку: в строку клиента подставили неверную потерю — скрипт вывел id клиента и обе стороны, код выхода 1.

## Ограничения

- Один снимок на N (зерно 1), настройки по умолчанию. Разные зёрна и веса отдельно не прогонялись; `parity.sh N SEED` принимает зерно.
- Сверка не входит в обязательный CI (нужен Python, 300k занимает минуту).
