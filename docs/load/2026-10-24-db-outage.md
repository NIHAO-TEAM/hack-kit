# Падение базы под залпом

Дата: 24.10. Изменение `db-outage-recovery`. Прогон — вручную: workflow `Deploy burst`, режим `outage` (`docs/load/outage.sh`).

**Статус: числа живого прогона не получены.** Исполнитель работал без Docker и PostgreSQL; ниже — что делается и что проверяется. После первого зелёного/красного прогона впишите сюда значения из артефакта `burst` (`pause/outage.json`, `kill/outage.json`, `probes.tsv`).

## Сценарий

Стенд Compose на раннере, снимок 100 000 клиентов, залп 10 000 событий (`rate=0`). Через 3 с PostgreSQL недоступен 10 с — дважды: `docker compose pause` (соединения висят) и `stop`/`start` (соединения рвутся); драйвер отдаёт разные ошибки.

## Что проверяет прогон

| Проверка | Ожидание |
|---|---|
| `/healthz` | `200` все пробы |
| `/readyz` | `503` все пробы, `200` после возврата |
| чтение очереди с сессией в кэше | `200` с `X-Data-Age`, пока жива запись кэша (`SESSION_CACHE_TTL`, 5 с); дальше `503` с `Retry-After` (без зависаний и `500`) |
| запрос с незнакомой сессией | `401` или `503` с `Retry-After`, не `500` |
| процесс | не перезапускался (`process_start_time_seconds`, `restartCount`) |
| события | `applied + failed = 10 000`, `failed = 0` |
| итог | согласованность, разница с пересчётом с нуля 0 центов |

## Что изменено

- `httpx.IsDBUnavailable`, `WriteFailure`: отказ соединения с базой — `503` + `Retry-After: 2`; ошибки запроса остаются `500`.
- `X-Data-Age` — секунды с последнего готового расчёта на `GET /api/…`.
- Писатель пачек: при недоступной базе повторы через 100 мс → 1 с → 5 с, затем ожидание `Ping` раз в секунду; очередь (4096) заполняется, и `submit` блокирует поток — обратное давление, события не теряются. Метрика `churn_ingest_db_unavailable_total`. Ошибка запроса — как раньше, один повтор.

## Оговорки

- Тесты политики повторов и `503` — юнит; остановку настоящего PostgreSQL проверяет только режим `outage`.
- Транзакция, у которой потерян ответ на `COMMIT`, при повторе заводит ещё одну версию данных: значения событий абсолютные, итог тот же.
