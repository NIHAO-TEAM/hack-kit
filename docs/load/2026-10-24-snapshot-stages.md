# Замер: загрузка снимка 100k по этапам

Сервер пишет длительность этапов `PUT /source/snapshot` в лог (`source: этапы загрузки: …`) и в метрику `churn_snapshot_ingest_stage_seconds{stage}`. Этап `read` слит с `parse`: тело читается потоком внутри разбора.

## Условия

- **Не стенд GitHub.** Контейнер разработки: Go-сервер `cmd/api` и PostgreSQL 16 (fsync включён) на одной машине, без Docker. Это не те 4 vCPU раннера из `2026-10-23-load-100k.md`, числа сравнимы только по порядку и по долям этапов.
- Данные: `cases/analizator/generate.py --accounts 100000 --services 300000 --transactions 1000000`, `data.json` 331 МБ.
- Три `PUT` подряд через `curl`, как в `docs/load/k6/snapshot.js`; после каждого идёт пересчёт.
- Запуск на стенде GitHub (`Deploy load`) сводку этапов не выводит: правка существующего workflow запрещена правилами исполнителя. Цифры стенда по этапам не получены (см. «Не сделано» в PR).

## Выбор правки (задача 2.1)

- Гипотеза «вторая и третья загрузки ждут блокировку из-за читателя пересчёта» **не подтвердилась**: `lock` и `truncate` — миллисекунды (редкий выброс `truncate` 0,94 с) на второй и третьей загрузке, пока шёл пересчёт. Отмена пересчёта не нужна, задача 2.3 не применима. Вторая загрузка во время пересчёта принимается и отменяет его (`TestLargeSnapshotLoad` с `LOAD_REPEAT=1`: второй PUT 10,2 с на 100k клиентов, пересчёт по старому снимку завершается `context canceled`).
- Главный этап — `copy_transactions` (≈ 8–10 с из 19–24), затем `parse` (6–9 с) и `copy_services` (≈ 2,6 с). Скорость `copy_*` определяют индексы и внешние ключи таблиц организаторов; убрать их — значит править схему, это вне изменения.
- Реализована кандидат Б: `CopyFromSlice` вместо предварительной сборки `[][]any` на 1,4 млн строк. По времени выигрыш в пределах шума (разброс трёх загрузок сократился: 19,2–23,6 → 19,6–20,2 с); выигрыш в памяти — не собираем 1,4 млн срезов `[]any` заранее.
- Рост 10× по данным дал рост ≈ 27× по времени в замере 23.10 (0,7 → 19 с на этой машине). Причину нелинейности (разбор JSON под нагрузкой GC, пересчёт на тех же ядрах) не установили.

## Итог

На этой машине загрузка 100k занимает ≈ 20 с при цели ≤ 30 с. **На стенде GitHub цифра не перемерена**: там было 44 с, и соотношение «машина разработки / раннер» неизвестно. Утверждать, что цель на стенде достигнута, нельзя. Следующий шаг, если стенд всё ещё выше 30 с: вывести этапы в summary `Deploy load` (правка workflow — решение человека) и сократить `parse` (потоковый разбор без промежуточных структур).
