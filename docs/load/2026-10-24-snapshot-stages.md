# Замер: загрузка снимка 100k по этапам

Сервер пишет длительность этапов `PUT /source/snapshot` в лог (`source: этапы загрузки: …`) и в метрику `churn_snapshot_ingest_stage_seconds{stage}`. Отдельного этапа `read` нет: тело читается потоком внутри `parse`.

## Условия

- **Не стенд GitHub.** Контейнер разработки: Go-сервер `cmd/api` и PostgreSQL 16 (fsync включён) на одной машине, без Docker. Это не те 4 vCPU раннера из `2026-10-23-load-100k.md`, числа сравнимы только по порядку и по долям этапов.
- Данные: `cases/analizator/generate.py --accounts 100000 --services 300000 --transactions 1000000`, `data.json` 331 МБ.
- Три `PUT` подряд через `curl`, как в `docs/load/k6/snapshot.js`; после каждого идёт пересчёт.
- Запуск на стенде GitHub (`Deploy load`) сводку этапов не выводит: правка существующего workflow запрещена правилами исполнителя. Цифры стенда по этапам не получены (см. «Не сделано» в PR).

## Выбор правки (задача 2.1)

- Гипотеза «вторая и третья загрузки ждут блокировку из-за читателя пересчёта» **в этом сценарии не подтвердилась**: `lock` и `truncate` — миллисекунды (выброс `truncate` 0,94 с на третьей загрузке). Это не значит «блокировки нет»: `Reader.Load` держит `REPEATABLE READ` только на чтение трёх таблиц, а загрузка 6–9 с разбирает тело до `TRUNCATE`, так что чтение обычно успевает закончиться раньше.
- Что реально происходит при втором PUT во время пересчёта: событие нового снимка лишь ставит `dirty` в `Engine` (`markDirty`); текущий пересчёт дорабатывает, затем идёт новый по новому снимку. Отмены пересчёта в коде нет. В замере `TestLargeSnapshotLoad` с `LOAD_REPEAT=1` второй PUT принят за 10,2 с.
- Нашлась ошибка на пересечении: `TRUNCATE transactions, services, accounts` брал блокировки в порядке, обратном `Reader.Load` (accounts, services, transactions). Если `TRUNCATE` приходил, пока читатель держал часть таблиц, PostgreSQL обрывал одного из них (`deadlock detected`), и загрузка отвечала 500. Порядок в `TRUNCATE` приведён к порядку читателя; тест `TestSnapshotIngestStagesAndSecondLoad`. Ошибка плавающая: на старом порядке тест падал не на каждом запуске (под `-race` упал, без него три запуска прошли).
- Главный этап по времени — `copy_transactions` (≈ 8–10 с из 19–24), затем `parse` (6–9 с) и `copy_services` (≈ 2,6 с). Скорость `copy_*` определяют индексы и внешние ключи таблиц организаторов; убрать их — значит править схему, это вне изменения.
- Реализован кандидат Б: `CopyFromSlice` вместо предварительной сборки `[][]any` на 1,4 млн строк. По времени выигрыш в пределах шума; разброс трёх загрузок сократился (19,2–23,6 → 19,6–20,2 с). Память до и после не замерялась, выигрыша по памяти не заявляем.
- Рост 10× по данным дал рост ≈ 27× времени (0,7 с в замере 23.10 на 10 000 → ≈ 19 с здесь на 100k). Причину нелинейности не установили.

## Итог

На этой машине загрузка 100k занимает ≈ 20 с при цели ≤ 30 с. **На стенде GitHub цифра не перемерена**: там было 44 с, и соотношение «машина разработки / раннер» неизвестно. Утверждать, что цель на стенде достигнута, нельзя. Следующий шаг, если стенд всё ещё выше 30 с: вывести этапы в summary `Deploy load` (правка workflow — решение человека) и сократить `parse` (потоковый разбор без промежуточных структур).
