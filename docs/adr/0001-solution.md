# ADR-0001: «Контур удержания» — объяснимый риск оттока с действием и ценой, встраиваемый в контур aéza

Статус: принято (Onisar, 23.10.2026, «да» в сессии пахана)
Дата: 2026-10-23
Заменяет: модель организации кита «компания → точки → роли» (`AGENTS.md`, раздел «Проект»; ADR-0003 из `docs/adr/README.md`) — для этого кейса

## Контекст

- Кейс «Анализатор рисков оттока» (aéza), `docs/case.md`: кому нужно внимание, почему, сколько денег теряем; обязательные пути, `/metrics`, Compose, вход по логину и паролю. Критерии жюри: бизнес-польза, обоснованность модели, архитектура и расширяемость, работоспособность, интерфейс.
- Эксперт aéza (`docs/experts/2026-10-23-aeza-chat.md`): «проверять все – от системного дизайна до деплоя в прод»; эндпоинты — «для удобства тестирования нами»; допы — после бизнес-задачи и в README; пользователи — сотрудники во внутреннем контуре; источник — REST API, SSO свой (FIDO, TOTP), Prometheus, Kubernetes, сдача — «репо + публичный домен».
- Данные (`cases/analizator/`): 10 / 30 / 100, истории статусов нет, опорная дата 2026-10-19T15:00Z, цена в генераторе случайна при любом периоде, все `prolong_wait` старше 5 дней.
- Сроки: стоп-кодинг 25.10 14:00 МСК (43 часа от 23.10 19:00), презентации 11:30, питч 16:00.
- Дебаты: `docs/decision/` (01a, 01b, 01_solution, r1_*, r2_*, 03_verdict) — KEEP WITH CHANGES, 3 из 3.

## Решение

Делаем «Контур удержания» по `docs/decision/01_solution.md` с обязательными правками `docs/decision/03_verdict.md`:

1. **Модель.** Признаки-плагины, риск услуги — шумовое ИЛИ, скор клиента — 100 · max по живым услугам; пороги 70 / 50; состояния «потерян» и «нет оценки» раздельно; `asOf` из снимка или максимум дат событий. ML не используем.
2. **Деньги.** Ожидаемая потеря за 30 дней = Σ P · R; рядом «под угрозой» и «уже потеряно»; правила подсчёта списаний в спеке, прототип-оракул и golden-тест.
3. **Изюминка.** Действие с ценой: для каждого клиента — одно действие и сколько евро оно снимет, посчитанное той же функцией на копии данных.
4. **Продукт.** Одна организация без компаний и точек. Роли: маркетолог (очередь и карточка), аналитик (модель и источник), администратор из `.env` (пользователи), учётка `jury` для проверки.
5. **Интеграция.** `PUT /source/snapshot` главнее всего; REST-адаптер биллинга и эмулятор — слой 2; `/metrics` для Prometheus; вход по паролю всегда, Keycloak-OIDC (FIDO2, TOTP) — второй кнопкой.
6. **Прод.** Compose + Caddy с TLS до контрольной точки (приёмка зелёная, час 25), затем k3s + Helm; Helm проверяется в CI с первого дня.
7. **Порядок работ** — три слоя с отсечкой (`03_verdict.md`, правка 10); всё вне обязательного — в README, раздел «Дополнительно».

## Последствия

- Проще: модель объясняется одной формулой, любое число воспроизводится оракулом; путь жюри (пароль → API) один и проверяется в CI; прод на Compose не зависит от k3s.
- Сложнее: модель организации кита не применяется — `review-prompt.md` и `backend/AGENTS.md` нужно поправить до этапа 3; два пути деплоя (Compose и Helm) нужно держать рабочими; цифры зависят от допущения `price_basis`.
- Проверяет: инварианты из `03_verdict.md` (401 без входа, путь `jury`, свойства скора, `/metrics` = summary, golden, настройки после рестарта, маршруты = спека). Пока `tests/invariants/` нет — гейта нет, их пишут люди.

## Отброшено

| Вариант | Почему нет |
|---|---|
| ML-модель | истории нет, обучать не на чем, на защите легко разбить |
| Взвешенная сумма признаков | шкала уплывает с каждым новым признаком |
| Свой WebAuthn и обязательный TOTP | ломает вход жюри по паролю, дорог, вне рубрики кейса; FIDO и TOTP даёт Keycloak |
| Две реплики, `LISTEN/NOTIFY` | гонки и время без баллов; путь масштабирования описан, не построен |
| Прод сразу на k3s | до зелёной приёмки требует реестр, Ingress, TLS и лимиты тела; 2 из 3 агентов против |
| Объединить с Invoice Keeper | эксперт: проверяют выбранный кейс, второй — только при равном качестве и как два сервиса |
| Кассовые разрывы (Центр-инвест) | у aéza живой контакт с экспертом и понятные ожидания |
