# ADR-0009: ядро в одном процессе Go; без брокера, Redis и ClickHouse

Статус: принято (Onisar, 24.10.2026: «Оформи» в сессии пахана после разбора Kafka; Redis и ClickHouse — по вопросу владельца в том же сообщении; `[lead]`)
Дата: 2026-10-24

## Контекст

- ADR-0001 и `backend/AGENTS.md`: модульный монолит на Go и PostgreSQL. Приём, пересчёт и выдача работают в одном процессе.
- Шина событий `internal/platform/events` — каналы Go внутри процесса. Событие на шине — только сигнал «данные изменились» или «пересчитано». Источник правды — таблицы PostgreSQL: потерянный сигнал закрывается следующим полным пересчётом по БД.
- Эксперт aéza (ADR-0004, п. 6): интереснее бэкенд и нагрузка, Go по максимуму. Жюри проверяет запуск через `docker compose up` (`docs/case.md`, п. 8).
- Конкурент ChurnRadar держит шесть сервисов на NATS JetStream и Redis (`docs/competitors.md`). Брокер нужен им для связи между сервисами.
- Узкие места у нас — запись в PostgreSQL и CPU расчёта, а не передача событий (`docs/load/`, проверено по коду: поток пишет снимок целиком — #155, список сортирует 100k на запрос — #147).
- Объём: 100 тыс. клиентов, 300 тыс. услуг, 1 млн транзакций (снимок 331 МБ). Аналитика считается в памяти после пересчёта, запросов по истории нет.
- Сессии читаются из PostgreSQL на каждый запрос (`internal/auth/service.go`, `authenticate`). Лимит попыток входа хранится в памяти процесса (`reserveAttempt`).

## Решение

1. **Шина — в памяти процесса, без брокера** (Kafka, NATS, RabbitMQ). Передача события — канал Go, без сети, сериализации и диска. Надёжность даёт PostgreSQL, а не журнал брокера.
2. **Redis не берём.** Горячие данные (очередь, сводка, карточки) уже лежат в памяти процесса в готовой модели чтения (`read-model-index`), и Redis был бы медленнее: сеть плюс сериализация. Сессии кэшируются в памяти процесса с коротким сроком: изменение `session-cache`. Выход из системы на других репликах вступает в силу в пределах этого срока.
3. **ClickHouse не берём.** Данных — единицы миллионов строк. Запросы — точечные записи и полная выборка снимка для пересчёта, а это профиль OLTP, и PostgreSQL с `COPY` его держит. Аналитических запросов по истории нет: истории оттока в данных кейса нет (ADR-0001).
4. **Внешняя шина aéza подключается адаптером источника.** Если биллинг aéza сам публикует события в Kafka, адаптер читает их топик рядом с REST-адаптером в `internal/source`, а ядро не меняется. Свою Kafka мы не поднимаем.
5. **Надёжность записи выбираем по виду данных.** Транзакции приёма потока событий эмулятора идут с `SET LOCAL synchronous_commit = off` (решение владельца 24.10: «да»): при падении сервера теряются последние миллисекунды подтверждённых событий, данные не портятся, после старта идёт полный пересчёт по БД. Загрузка снимка, настройки модели, сессии и аудит остаются с синхронной фиксацией.

## Последствия

- Проще: в Compose и Helm только приложение и PostgreSQL. Событие доходит до пересчёта за микросекунды. Меньше способов, которыми стенд жюри не поднимется.
- Сложнее:
  - Масштабирование — вертикальное, по ядрам одного процесса. Несколько реплик (`pod-kill-under-load`) каждая считают свою копию результата по общей БД; согласованность проверяется сравнением сводок.
  - Лимит попыток входа и кэш сессий живут в каждой реплике отдельно: с двумя репликами попыток входа вдвое больше.
  - Сигналы шины не переживают рестарт процесса. Это допустимо: после старта идёт полный пересчёт по БД.
- Проверяет: depguard (`platform` не импортирует домен); тест согласованности потока с пересчётом с нуля (`events-stream-emulator`, `event-ingest-delta`); залп под нагрузкой (`load-burst-proof`).

## Когда пересмотреть

| Условие | Что брать |
|---|---|
| биллинг aéza отдаёт события в Kafka | адаптер-потребитель в `internal/source` (п. 4), не свою шину |
| расчёт не помещается в одну машину (миллионы клиентов, пересчёт дольше минуты на всех ядрах) | разбиение по клиентам и брокер между репликами |
| копится история событий для калибровки и нужны запросы по времени на сотнях миллионов строк | ClickHouse как хранилище истории, рядом с PostgreSQL |
| реплик больше двух и общий лимит входа обязателен | общий счётчик в PostgreSQL или Redis |

## Отброшено

| Вариант | Почему нет |
|---|---|
| Kafka как шина | один процесс: сеть, диск и сериализация добавляют задержку и не дают пропускной способности; второй журнал рядом с БД — двойная запись; от 1 ГБ памяти и отдельный сервис в Compose |
| NATS JetStream (как у ChurnRadar) | легче Kafka, но причина та же: связывать нечего, сервис один |
| Redis для кэша данных | данные уже в памяти процесса; Redis медленнее и ещё один сервис |
| Redis для сессий | кэш в памяти с коротким сроком даёт тот же выигрыш без сервиса |
| ClickHouse для аналитики | нет истории и запросов по времени; объём для PostgreSQL небольшой |
