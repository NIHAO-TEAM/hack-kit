# Архитектура

Одна страница для жюри. Решения — [adr/](adr/), правила частей — `backend/AGENTS.md`, `frontend/AGENTS.md`, контракт — `api/openapi.yaml`.

## Схема потоков

Ядро — один процесс Go на всех ядрах (ADR-0009): приём, пересчёт и выдача работают в одной памяти, без сети между ними. Источник правды — PostgreSQL.

```
биллинг aéza / эмулятор                     жюри, Swagger
  │ снимок: PUT /api/v1/source/snapshot (потоком, обратное давление)
  │ правки: PATCH услуг и аккаунтов, опрос REST-биллинга (BILLING_URL)
  │ поток событий эмулятора: точечная запись пачками в одной транзакции
  ▼
 source ──────► PostgreSQL (снимок, настройки, пользователи, сессии, аудит)
  │ событие «данные изменились» — канал шины в памяти (platform/events)
  ▼
 пересчёт (app/recalc): пачки клиентов → воркеры по числу ядер, отмена при свежих данных,
  │  склейка событий; risk: признаки → P → скор → уровень → деньги → действия
  │ результат + сводка, событие «пересчитано»
  ▼
 analytics: неизменяемый результат (atomic-указатель), чтение без блокировок
  ├─► REST: /customers, /customers/{id}, /analytics/summary, /analytics/churn-chart
  ├─► SSE:  /api/v1/events (сигнал с категориями — фронт сбрасывает ключи запросов)
  └─► /metrics (Prometheus, по токену) ──► Prometheus ──► Grafana «Контур удержания», «Внутри сервиса»
  ▼
 веб-клиент (React): очередь, карточка, сводка, модель, о модели, источник
```

Смена настроек модели (`PATCH /api/v1/model/settings`) запускает тот же пересчёт. Каждый прогон потока событий заканчивается сверкой: результат сервиса против пересчёта с нуля по итоговому снимку, разница в центах должна быть 0.

## Почему один процесс

- Событие на шине — только сигнал «пересчитай»; данные уже в PostgreSQL. Потерянный сигнал закрывает следующий пересчёт, поэтому брокер (Kafka, NATS) не нужен: связывать нечего.
- Горячие данные лежат в памяти процесса в готовом результате; Redis был бы медленнее (сеть). Сессии кэшируются в памяти на 5 с.
- Объём — единицы миллионов строк текущего снимка; запросов по истории нет, поэтому ClickHouse не нужен.
- Когда пересматривать (портфель не помещается в одну машину, у aéza есть своя шина, копится история) — ADR-0009, «Когда пересмотреть».
- Замеры с железом и командами — `docs/load/` (README раздела «Нагрузка»).

Задачи удержания (данные и API без интерфейса — ADR-0004: CRM в продукте не делаем) идут отдельным контуром (`backend/internal/retention`): после каждого пересчёта (тема шины `recalculated`) наблюдатель сравнивает открытые задачи с новыми данными клиента и дописывает наблюдения в историю; запись по задаче публикует тему `tasks`, и SSE сообщает клиенту, что списки задач надо перечитать.

```
пересчёт ──► тема recalculated ──► retention.Observe: открытая задача × текущий клиент
                                        │ новые наблюдения (ключ не повторяется)
                                        ▼
                         retention_task_events ──► тема tasks ──► SSE /api/v1/events
```

Смена настроек модели (`PATCH /api/v1/model/settings`) запускает тот же пересчёт.

## Модули

| Модуль | Роль |
|---|---|
| `backend/internal/source` | приём и хранение снимка источника, проверка данных |
| `backend/internal/risk` | чистая модель: признаки, скор, уровни, деньги, действия; реестры расширяются файлом |
| `backend/internal/model` | настройки модели (веса, пороги, горизонт), версионирование |
| `backend/internal/analytics` | движок результатов и HTTP: очередь, сводка |
| `backend/internal/app` | пересчёт: собирает снимок и настройки, вызывает `risk`, публикует событие |
| `backend/internal/retention` | задачи удержания и их история (API и данные для будущей калибровки, интерфейса нет — ADR-0004) |
| `backend/internal/auth` | вход, сессии, роли и права, проверка на сервере для каждой операции |
| `backend/internal/platform` | шина событий, часы стенда, БД, HTTP-обвязка, Swagger |
| `frontend/` | клиент: FSD-слои, типы из `openapi.yaml`, моки MSW |
| `tools/oracle` | эталонный расчёт модели на Python, сверка с golden |

Модуль `risk` не знает о БД и HTTP: на входе снимок и настройки, на выходе числа. Поэтому его проверяют golden-тесты до цента против независимой реализации (оракул).

### Модуль задач удержания (без интерфейса, ADR-0004)

- **Отдельно от снимка.** Снимок источника заменяется целиком, поэтому у `retention_tasks` и `retention_task_events` нет внешних ключей на таблицы снимка (`backend/migrations/20261024100000_retention_tasks.sql`). Задача хранит `customer_id` и `customer_email` и переживает смену снимка.
- **Связь с клиентом — по ID и email.** Если в текущем снимке клиента с таким ID нет или email другой, у задачи `customerMissing = true` (`service.go`): чужого клиента под старой задачей не показываем.
- **Одна открытая задача на клиента.** Гонку двух «взять в работу» решает частичный уникальный индекс `retention_tasks_one_open_idx` (`status <> 'closed'`), а не проверка в коде.
- **Оптимистичная блокировка.** Поле `version` растёт на каждой правке; правка со старой версией получает 409, молчаливой перезаписи нет.
- **Исходное состояние.** При взятии в работу в `baseline` сохраняются уровень, скор, ожидаемая потеря, баланс и услуги клиента; наблюдения считаются как разница между `baseline` и текущими данными (`observe.go`, чистая функция без базы и часов).
- **Журнал событий.** `created`, `changed`, `contact`, `note` пишет сотрудник, `observed` — сервер (`system`). Ключ наблюдения `obs_key` уникален в задаче, поэтому повторный пересчёт не дублирует запись.
- **Метрики.** `churn_retention_tasks`, `churn_retention_tasks_overdue`, `churn_retention_tasks_closed_total`, `churn_retention_expected_loss_in_work_cents` (`metrics.go`).

## Контракт

`api/openapi.yaml` — единственный источник: из него генерируются код сервера (`oapi-codegen`) и типы фронта (`openapi-typescript`). CI проверяет, что генерация не даёт диффа, и ловит ломающие правки контракта (`oasdiff`).

## Деплой

- Прод: k3s на одном сервере, Helm-чарт `deploy/helm/churn` (приложение, PostgreSQL, Ingress на Traefik с TLS Let's Encrypt, сетевые политики, ServiceMonitor). Выкат — `deploy-k8s.yml` (образ, `helm upgrade`), после него проверки `deploy-ingress`, `deploy-smoke`, `deploy-a11y`, `deploy-layout`, `deploy-readme-check`.
- Keycloak, Grafana и Prometheus — в Compose на том же хосте, подключены к Traefik (раздел «Прод после перехода на k3s» ниже).
- Образ distroless, бинарь собран по профилю (PGO, `cmd/api/default.pgo`), `GOMEMLIMIT` задан ниже лимита памяти пода (`values.yaml`).
- Локально и у жюри: `docker compose up -d` (README); стенд демо-сценария в CI — `demo-e2e.yml`.
- Kubernetes здесь не для скорости (скорость даёт Go на всех ядрах), а для выката без простоя, проверок готовности и установки в контур aéza правкой `values.yaml`.

## Остановка и готовность

`cmd/api/main.go` берёт корневой `context` от `SIGINT`/`SIGTERM` и отдаёт его воркерам пересчёта и опроса биллинга. Порядок остановки (`serve`): сигнал → `GET /readyz` отвечает `503` → пауза `SHUTDOWN_DRAIN` (5 с, балансировщик снимает под) → `srv.Shutdown` с таймаутом `SHUTDOWN_TIMEOUT` (20 с): идущие запросы дорабатывают, потоки SSE получают `retry` и закрываются → ожидание воркеров → закрытие пула БД.

`/readyz` (`internal/platform/httpx/lifecycle.go`, вне Swagger, без сессии) отвечает `200`, когда есть первый результат пересчёта и база отвечает на ping; `/healthz` не меняется и остаётся пробой живости. Helm: `readinessProbe` на `/readyz`, `terminationGracePeriodSeconds: 40` больше суммы пауз. Метрика `churn_shutdown_inflight` — запросов в работе на момент сигнала; сервер имеет `ReadTimeout` 30 с и `IdleTimeout` 120 с, у потока `/api/v1/events` дедлайны сняты.

## Безопасность

- Роли и права проверяются на сервере для каждой операции (ADR-0001); интерфейс лишь скрывает недоступное.
- Задачи удержания: читать (`GET /tasks`, `/tasks/{id}`, исполнители) может любая роль; создавать и менять (`POST /customers/{id}/task`, `PATCH /tasks/{id}`, `POST /tasks/{id}/events`) — маркетолог, `jury`, администратор; аналитик только читает (`backend/internal/auth/permissions.go`).
- В журнале действий (`GET /api/v1/audit`) действия `taskCreated`, `taskChanged`, `taskRecorded` пишутся без email клиента и без текстов заметок.
- Пароли хэшируются, сессии — в cookie с защитой от CSRF, у входа — ограничение частоты.
- Секреты только из переменных окружения (`.env` не коммитится); `/metrics` и приём снимка — по токену.
- TLS — на Traefik (Let's Encrypt); заголовки безопасности (CSP, HSTS, X-Frame-Options) ставит приложение (`internal/platform/httpx/security.go`); база наружу не публикуется.
- Пользовательские данные в логах не печатаются.

## Чего мы не утверждаем

- **Наблюдение — не причина.** Запись «услуга продлена после контакта» говорит, что после взятия в работу в данных биллинга что-то изменилось. Она не говорит, что продление — результат контакта: клиент мог продлить и без звонка.
- **ROI контакта не считается.** Исход задачи (`renewed`, `refused`, …) выставляет человек, деньги «в работе» — ожидаемая потеря по модели, а не подтверждённая сохранённая выручка.
- **Что нужно, чтобы утверждать.** История контактов за достаточный срок, сопоставимая контрольная группа клиентов того же риска, которых не трогали, и сравнение доли продлений в группах. Сейчас этих данных нет.

## Как встать в контур aéza

1. Источник данных: снимок на `PUT /api/v1/source/snapshot` с токеном `SOURCE_TOKEN` (формат — `api/openapi.yaml`) и/или опрос REST-биллинга (`BILLING_URL`, `BILLING_TOKEN`). Если биллинг публикует события в шину — адаптер-потребитель в `internal/source` (ADR-0009, п. 4), ядро не меняется.
2. Развёртывание: Helm-чарт `deploy/helm/churn`, пример — `values-aeza.example.yaml`: образ, домен, секреты, лимиты.
3. Вход сотрудников: OIDC (Keycloak с TOTP) — `OIDC_*`; локальные учётки остаются запасным входом.
4. Мониторинг: Prometheus снимает `/metrics` с токеном `METRICS_TOKEN`; дашборды Grafana — `deploy/grafana/dashboards`.

## Проверка входа через Keycloak

Автоматически (TOTP): `e2e/tests/sso.spec.ts` против Compose с профилем `sso` или прода с Keycloak. Нужны `E2E_BASE_URL`, `E2E_SSO_PASSWORD` (`KC_SECURE_PASSWORD`) и `E2E_SSO_TOTP_SECRET` (`KC_SECURE_TOTP_SECRET`). У пользователя `secure` TOTP заведён при импорте realm, секрет — из `.env`, не из репозитория.

На проде: `https://<домен>/sso/realms/churn/.well-known/openid-configuration` отвечает `200`, `/sso/admin` — `404`. Realm импортируется один раз; чтобы подхватить `KC_SECURE_TOTP_SECRET` на проде с уже созданным realm, допишите переменную в `.env` и пересоздайте том `kcdata`.

Ключ доступа (WebAuthn) тестом не проверяется: в Firefox Playwright нет виртуального аутентификатора. Шаги для человека:

1. Войти в Keycloak как `secure` (пароль + код TOTP) на `https://<домен>/sso/realms/churn/account`.
2. «Вход в аккаунт» → «Беспарольный вход / ключ доступа» → добавить ключ (Touch ID, Windows Hello или ключ безопасности).
3. Выйти, на экране входа панели нажать «Войти через SSO»; Keycloak предлагает ключ доступа вместо пароля.
4. Подтвердить ключ — откроется очередь с ролью маркетолога.

## Прод после перехода на k3s

- Приложение и база — в k3s (чарт `deploy/helm/churn`), вход один: Traefik на 80/443.
- Keycloak (`/sso`), Grafana (`/grafana`) и Prometheus остались в Compose (`deploy/docker-compose.prod.yml`): порты `18080`, `13000`, `19090` слушают только на `COMPANIONS_BIND` (адрес docker0), снаружи закрыты. В Traefik они подключены через Service без селектора и EndpointSlice (`templates/companions.yaml`); админка Keycloak и master-realm закрыты.
- Prometheus опрашивает `/metrics` через Traefik по `https://<домен>` с bearer-токеном (`METRICS_TARGET`, `METRICS_SCHEME` в `~/churn/.env`).
- Включает всё это `deploy/k3s/single-ingress.sh`; состояние смотреть через `deploy/k3s/diagnose.sh`.
