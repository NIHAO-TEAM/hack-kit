# Архитектура

Одна страница для жюри. Решения — [adr/](adr/), правила частей — `backend/AGENTS.md`, `frontend/AGENTS.md`, контракт — `api/openapi.yaml`.

## Схема потоков

[ПРЕДПОЛОЖЕНО] Схема — целевая: приём снимка, пересчёт и модель в `main`; SSE, `/metrics`, график и эмулятор приходят изменениями этапов 4–6 (`docs/plan.md`).

```
источник (биллинг / эмулятор)
      │  снимок: PUT /api/v1/source/snapshot, правки услуг и аккаунтов
      ▼
 source ──────► Postgres (снимок, настройки, пользователи, сессии)
      │ событие «данные изменились»
      ▼
 шина событий (внутри процесса)
      │
      ▼
 пересчёт (app/recalc) ── risk: признаки → P → скор → уровень → деньги → действия
      │ результат клиентов и сводка
      ▼
 analytics  ──► REST: /customers, /analytics/summary, /analytics/churn-chart
      │      ──► SSE:  /api/v1/events  (сигнал с категориями — фронт сбрасывает ключи Query)
      │      ──► /metrics (Prometheus, по токену)
      ▼
 веб-клиент (React): очередь, карточка клиента, сводка, модель, источник
```

Смена настроек модели (`PATCH /api/v1/model/settings`) запускает тот же пересчёт.

## Модули

| Модуль | Роль |
|---|---|
| `backend/internal/source` | приём и хранение снимка источника, проверка данных |
| `backend/internal/risk` | чистая модель: признаки, скор, уровни, деньги, действия; реестры расширяются файлом |
| `backend/internal/model` | настройки модели (веса, пороги, горизонт), версионирование |
| `backend/internal/analytics` | движок результатов и HTTP: очередь, сводка |
| `backend/internal/app` | пересчёт: собирает снимок и настройки, вызывает `risk`, публикует событие |
| `backend/internal/auth` | вход, сессии, роли и права, проверка на сервере для каждой операции |
| `backend/internal/platform` | шина событий, часы стенда, БД, HTTP-обвязка, Swagger |
| `frontend/` | клиент: FSD-слои, типы из `openapi.yaml`, моки MSW |
| `tools/oracle` | эталонный расчёт модели на Python, сверка с golden |

Модуль `risk` не знает о БД и HTTP: на входе снимок и настройки, на выходе числа. Поэтому его проверяют golden-тесты до цента против независимой реализации (оракул).

## Контракт

`api/openapi.yaml` — единственный источник: из него генерируются код сервера (`oapi-codegen`) и типы фронта (`openapi-typescript`). CI проверяет, что генерация не даёт диффа, и ловит ломающие правки контракта (`oasdiff`).

## Деплой

- Прод: Docker Compose — Postgres, приложение (один бинарь Go, фронт внутри), Caddy с TLS Let's Encrypt (`deploy/docker-compose.prod.yml`, `deploy/Caddyfile`). Наружу только 80 и 443; база и приложение — во внутренней сети Compose.
- Деплой запускает workflow `deploy.yml` по SSH-ключу из секрета; образ distroless, проверка здоровья — сам бинарь.
- Локально: `docker compose up -d` (см. README).
- Слой 2 (этап 6): k3s и Helm-чарт; см. `docs/plan.md`.

## Безопасность

- Роли и права проверяются на сервере для каждой операции (ADR-0001); интерфейс лишь скрывает недоступное.
- Пароли хэшируются, сессии — в cookie с защитой от CSRF, у входа — ограничение частоты.
- Секреты только из переменных окружения (`.env` не коммитится); `/metrics` и приём снимка — по токену.
- TLS и заголовки безопасности — на Caddy; приложение не публикуется напрямую.
- Пользовательские данные в логах не печатаются.

## Как встать в контур aéza

1. Источник данных: направить биллинг на `PUT /api/v1/source/snapshot` (формат — `api/openapi.yaml`, схема снимка) с токеном `SOURCE_TOKEN`; либо подключить REST-адаптер биллинга (изменение `billing-rest-adapter`).
2. Задать окружение: `POSTGRES_PASSWORD`, `ADMIN_*`, токены — по `.env.example`.
3. Вход сотрудников: локальные учётки; OIDC через Keycloak — изменение `keycloak-oidc`.
4. Развёртывание в кластере: Helm-чарт с `values.yaml` (изменение `helm-k3s`): образ, домен, секреты, токен метрик; Prometheus снимает `/metrics`.

[ПРЕДПОЛОЖЕНО] Пункты 1, 3, 4 описывают план этапа 6: на момент записи этих изменений в `main` нет, документ обновляется вместе с ними.

## Проверка входа через Keycloak

Автоматически (TOTP): `e2e/tests/sso.spec.ts` против Compose с профилем `sso` или прода с Keycloak. Нужны `E2E_BASE_URL`, `E2E_SSO_PASSWORD` (`KC_SECURE_PASSWORD`) и `E2E_SSO_TOTP_SECRET` (`KC_SECURE_TOTP_SECRET`). У пользователя `secure` TOTP заведён при импорте realm, секрет — из `.env`, не из репозитория.

На проде: `https://<домен>/sso/realms/churn/.well-known/openid-configuration` отвечает `200`, `/sso/admin` — `404`. Realm импортируется один раз; чтобы подхватить `KC_SECURE_TOTP_SECRET` на проде с уже созданным realm, допишите переменную в `.env` и пересоздайте том `kcdata`.

Ключ доступа (WebAuthn) тестом не проверяется: в Firefox Playwright нет виртуального аутентификатора. Шаги для человека:

1. Войти в Keycloak как `secure` (пароль + код TOTP) на `https://<домен>/sso/realms/churn/account`.
2. «Вход в аккаунт» → «Беспарольный вход / ключ доступа» → добавить ключ (Touch ID, Windows Hello или ключ безопасности).
3. Выйти, на экране входа панели нажать «Войти через SSO»; Keycloak предлагает ключ доступа вместо пароля.
4. Подтвердить ключ — откроется очередь с ролью маркетолога.
