# r1_B. Скептик: почему 01_solution провалится на защите

Агент B, раунд 1. Источники: `docs/case.md`, `docs/decision/01_solution.md`, `00_audit.md`, `01b.md`, `docs/experts/2026-10-23-aeza-chat.md`, `cases/analizator/`. Скрипты пересчёта лежат вне репозитория (scratchpad сессии): `score.py` реализует формулы 01_solution, `bench.py` замеряет время на наборе 100k.

## Пять причин провала (пре-мортем)

### 1. P0. Жюри не смогло войти логином и паролем
- Источники: кейс, «Обязательные возможности», п. 9 («Вход по логину и паролю защищает панель и API»), таблица авторизации (`POST /auth/login`). Эксперт, ответ 1: «эпы сделаны для удобства тестирования нами».
- 01_solution: «TOTP обязателен для аналитика и администратора», плюс WebAuthn. Скрипт жюри шлёт `POST /auth/login` с логином и паролем и получает «нужен второй фактор» вместо сессии. После этого `PATCH /model/settings` (п. 3 и пункт приёмки «Коэффициенты») недоступен по паролю. Ключа FIDO у жюри нет.
- [ПРОВЕРЕНО по тексту]: противоречие с критерием приёмки, без которого «решение не принимается».
- Что сделать: логин с паролем выдаёт полную сессию. Второй фактор — флаг пользователя, включается в профиле. Учётки жюри в README без второго фактора, вход с TOTP показываем на отдельной учётке. Свой WebAuthn вырезать (см. п. 5).

### 2. P1. Не успели прод, потому что объём рассчитан не на 43 часа
- Источники: эксперт, ответ 5 («должно быть в проде доступно нам»); сервера и домена пока нет; `team.md`: не больше 11 изменений одновременно, исполнители — Sonnet.
- [ГИПОТЕЗА] Список: обязательные эндпоинты, модель, деньги, SSE, `/metrics`, панель на 4 экрана, эмулятор биллинга, REST-адаптер с курсором, TOTP, WebAuthn, роли, экран пользователей, журнал, CSV, dryRun, график оттока, проверки качества данных, Helm, k3s, cert-manager, NetworkPolicy, ServiceMonitor, Grafana, Trivy, k6, две реплики с LISTEN/NOTIFY. Это 35–45 изменений. Цепочка контракт → каркас → скоринг → API → UI → деплой последовательная, а `api/openapi.yaml` защищён и общий для всех, поэтому правки контракта идут по одной. Сервер выдадут неизвестно когда, а WebAuthn и cert-manager не проверить без домена.
- Что сделать: прод в два шага. Шаг 1 (сразу как дадут VM): Compose + Caddy с автоматическим TLS, наружу только 443, Postgres без порта. Шаг 2, если хватит времени: k3s + Helm. Чарт лежит в репо при любом исходе. Порядок резки — в конце.

### 3. P1. Жюри не поверило денежной цифре
- Источники: кейс, «Денежная оценка» («понятное объяснение её смысла»); критерий «обоснованность модели».
- [ПРОВЕРЕНО] 99,8 % потери №9 даёт одна услуга №19: почасовая `suspended` за 8,55 €/ч (6164 €/мес), срок истёк 59 дней назад. При другой трактовке `price` вместо 3895 € получается 50,66 €.
- [ПРОВЕРЕНО] Цифра на стенде названа «3900 € **под угрозой**», а в разделе «Деньги» «под угрозой» = Σ R по среднему и высокому риску = **6931,84 €**. «Ожидаемая потеря» = 3894,56 €. Два разных числа носят одно имя, член жюри с калькулятором это поймает.
- [ПРОВЕРЕНО] Правила подсчёта неоднозначны: 720 или 721 списание, сколько платежей у просроченной `suspended`. Golden-тест по числам 01b будет красным у любой «правильной» Go-реализации.
- Что сделать: (а) спросить эксперта, за что `price` у `hour`; (б) везде подписать «ожидаемая потеря 3895 €» и «под угрозой 6932 €»; (в) записать правило подсчёта списаний в спеку (`[asOf, asOf+H]`, обе границы; для просроченной не-`prolong_wait` — одно списание в asOf, дальше шаг от asOf), положить прототип в репо как оракул и снимать golden с него, а не из текста.

### 4. P1. На данных жюри нет уровня «низкий», а «средний» держится на шуме
- Источники: кейс, «Веб-панель», п. 1 («высокий, средний или низкий уровень риска»), критерий «Панель и рейтинг».
- [ПРОВЕРЕНО] Расклад 3 / 3 / 0 / 4. №6 стоит на 45,95 при пороге 45, причём из-за `fail` = 1 у годовой услуги, созданной 30 минут назад и оплаченной до 2027-10-19 (потеря 2,20 €). При среднем пороге 50 получается 3 / 2 / 1 / 4: №6 становится низким, низкий уровень виден сразу.
- [ПРОВЕРЕНО] На 100k: высокий 37,5 %, средний 16,1 %, низкий 6,4 %, нет оценки 40 %. Высоким оказывается 62 % оценённых клиентов. Причина в генераторе: все `prolong_wait` созданы за 400 дней до опорной даты, поэтому `pwait` всегда равен 1, а `fail` у каждой услуги равен 0 или 1. На вопрос «кому нужно внимание» ответ «почти всем».
- Что сделать: средний порог 50. Очередь по умолчанию сортировать по потере (уже так). Для наглядности эмулятор должен порождать свежие `prolong_wait` (2–4 дня до удаления): кейс разрешает «расширенный для наглядности» набор. Без этого ступенька `1 − осталось/5` и таймер «до удаления 2 д 7 ч» на данных жюри не видны ни разу: все 6 `prolong_wait` просрочены на 35–400 дней.

### 5. P1. «Другая команда сделала то же шире»
- Источник: кейс, «Дополнительные возможности»: явные бонусы — OIDC, график оттока, UX.
- [ГИПОТЕЗА] 01_solution отодвигает OIDC, указанный бонус, в конец. Силы уходят в свои TOTP и WebAuthn, которых в списке бонусов нет, и обоснование держится на одной фразе эксперта. Типичная сильная команда поставит Keycloak-OIDC, Grafana и аккуратную таблицу. Тогда она получит бонус, которого у нас нет, а наш довесок жюри не засчитает.
- Что сделать: Keycloak (или Dex) в Compose-профиле `sso`. Он даёт OIDC (бонус кейса), TOTP и WebAuthn (то, что назвал эксперт) без своего крипто-кода. Вход по паролю в приложении остаётся (п. 1). Сэкономленные часы вложить в то, чего у других не будет: деньги и действия с ценой.

## Предварительный вердикт: KEEP WITH CHANGES

Ядро верное, цифры воспроизводятся: шумовое ИЛИ, max по услугам, деньги через P·R, действия с ценой, «нет оценки». Валят решение не модель, а вход (п. 1), объём (п. 2) и подписи к деньгам (п. 3). Всё это чинится дёшево.

Обязательные правки до старта: вход по паролю даёт полную сессию; второй фактор опционален; средний порог 50; явный `asOf`; спека правил подсчёта списаний и прототип-оракул в репо; `bigint`; разные имена у «ожидаемой потери» и «под угрозой».

**Что резать при отставании, в этом порядке:**
1. Свой WebAuthn (и свой TOTP, если появится Keycloak).
2. Две реплики, LISTEN/NOTIFY: одна реплика, SSE из процесса.
3. k3s, Helm, cert-manager, NetworkPolicy, ServiceMonitor: остаётся прод на Compose + Caddy (TLS, только 443).
4. REST-адаптер с курсором `updatedAt`: эмулятор шлёт `PUT /source/snapshot` или правку одной услуги.
5. Экран пользователей, журнал изменений, CSV, «в работе», плагины качества данных, Trivy, k6.
6. dryRun-предпросмотр.

Не резать: обязательные эндпоинты и Swagger, модель и деньги с пояснением, два действия с ценой (№9 и №1), SSE, `/metrics`, график оттока (бонус кейса), README и прод по публичному домену.
